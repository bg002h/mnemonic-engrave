SeedHammer II

Build a Bitcoin wallet policy on a device that isn't here.

Below is the actual firmware — the same Go code that runs on the machine, compiled to WebAssembly. Not a mock, not a video, not a reimplementation of the screens. Tap it and it behaves exactly as the hardware does, because it is the hardware's software.

Pick something to build

Each one ends with a Template-ID: a 128-bit fingerprint of your policy's shape.

Everything here is throwaway test data. The seeds, shares and passphrases on this page are published test vectors. Nothing on this page touches money, and nothing you do here can.

Then try it on your own machine

The device is one half. The other half is a set of command-line tools that compose the same policies, turn them into engravable strings, and check the device's work. Two of them are worth ten minutes of your time.

On macOS, the first run will be blocked. These binaries are not notarised by Apple, so Gatekeeper quarantines them on download. Clear it once with xattr -d com.apple.quarantine ./md ./ms — or right-click the file and choose Open. Nothing is wrong with the binary.
Check what you downloaded. Each release ships SHA256SUMS.portable: shasum -a 256 -c SHA256SUMS.portable --ignore-missing. A checksum proves the file arrived intact — it does not prove who made it. Of these, only mnemonic-engrave is signed.

One more tool: mnemonic, the Swiss-army knife

The recovery searches below — and the John the Ripper pipeline — use mnemonic from mnemonic-toolkit. Prebuilt like md and ms: the crate is mnemonic-toolkit, the binary is mnemonic.

One version, every platform. macOS, Windows and Linux musl all ship from the same release — the version-split that used to send Linux users to an older build is gone. The musl builds are signed and reproducible. On macOS clear Gatekeeper once with xattr -d com.apple.quarantine ./mnemonic.

Install the version linked above — the short-id behaviour in §3b below is recent. On an older binary a short --expect-wallet-id is refused outright rather than listing.

1  Split a seed three-of-five, then prove any three is sufficient and any two isn't enough

codex32 (BIP-93) is Shamir's secret sharing over the bech32 alphabet. Five shares; any three rebuild the seed, any two rebuild nothing. Don't take the word “any” on trust — there are only twenty cases, so check every one of them. 

# A published all-zeros test vector. Never do this with a real seed.
echo "abandon abandon abandon abandon abandon abandon abandon abandon abandon abandon abandon about" > seed.txt

ms split --in seed.txt -k 3 -n 5 --group-size 0 > shares.txt
# 5 lines, each starting ms13... — different every run, they're randomised

# one combination in full, so you can see what coming back looks like
sed -n '1p;3p;5p' shares.txt > three.txt
ms combine --in three.txt
entropy: 00000000000000000000000000000000
phrase: abandon abandon ... about
language: english (12 words)

Now every combination there is. Five shares give exactly ten ways to pick three and ten ways to pick two — small enough to be exhaustive rather than illustrative: 

# all 10 ways to pick three — each must rebuild the seed byte for byte
for t in 123 124 125 134 135 145 234 235 245 345; do
  sed -n "$(echo "$t" | sed 's/./&p;/g')" shares.txt > pick.txt
  got=$(ms combine --in pick.txt 2>/dev/null | sed -n 's/^phrase: //p')
  [ "$got" = "$(cat seed.txt)" ] && printf "%s ok  " "$t" || printf "%s FAIL  " "$t"
done; echo
123 ok  124 ok  125 ok  134 ok  135 ok  145 ok  234 ok  235 ok  245 ok  345 ok

# all 10 ways to pick two — each must rebuild nothing at all
for p in 12 13 14 15 23 24 25 34 35 45; do
  sed -n "$(echo "$p" | sed 's/./&p;/g')" shares.txt > pick.txt
  ms combine --in pick.txt >/dev/null 2>&1 && printf "%s LEAKED  " "$p" || printf "%s refused  " "$p"
done; echo
12 refused  13 refused  14 refused  15 refused  23 refused  24 refused  25 refused  34 refused  35 refused  45 refused

Twenty for twenty. The threshold isn't a rule the software is choosing to enforce — two shares do not contain the seed, so there is nothing for any tool, or anyone holding them, to extract.

Prove the check isn't hollow. A test that can only pass proves nothing. Damage one share — cp shares.txt shares.bak and flip one character of share 2 to a different one — old=$(sed -n 2p shares.txt|cut -c40); sed -i "2s/./$([ "$old" = q ] && echo p || echo q)/40" shares.txt — and re-run the first loop. Exactly the six triples containing share 2 flip to FAIL, and the four that avoid it (134 135 145 345) still say ok. That is the loop reading the shares, not printing a foregone conclusion. cp shares.bak shares.txt to carry on.

That string below is a real wallet policy — the zen-hodl wallet from the third mission, one key that cannot spend anything younger than 32,768 blocks. Metal gets scratched, so the encoding carries error correction: it repairs up to four wrong characters and tells you exactly which.

3  Check the device's work against a second implementation

The repaired string is that same zen-hodl wallet. Ask the command-line tool for its identity, and compare it with what the device showed you after mission 3. The device's firmware is Go; this tool is Rust. They were written to the same specification and never share a line of code. 

md inspect md1yqfdsssjuqqcr5e55uqqqgqqq6qqvf4d7h59r2
template: tr(50929b74...ac0,and_v(v:pk(@0/<0;1>/*),older(32768)))
wallet-descriptor-template-id: 73c33a5dea17b45376a6246995df0cbb
wallet-policy-id:              891b6c372c99c033c98bc80604deb6f0

Two independent implementations agreeing, to the bit, on what your wallet is. That is the whole point of a template identity.

4  Two recoveries, for when something has gone wrong

These come from mnemonic-toolkit, the constellation's larger tool. They answer the questions people actually turn up with.

“I forgot my passphrase”

You have the seed and the wallet's xpub, and a shortlist of what the passphrase might have been. 

# one candidate per line -- this file is SECRET, it holds guesses at your passphrase
printf 'hunter2\ncorrect horse\nbitcoin\nsatoshi\nnakamoto\n' > candidates.txt

printf '<your 12 words>' | mnemonic xpub-search passphrase-of-xpub   --phrase-stdin --passphrase-candidates-file candidates.txt   --target-xpub <your xpub>
match: candidate on line 4 derives the target xpub at m/84'/0'/0'
searched: 140 candidate paths per passphrase

It tries each line against the standard path templates across an account range and stops at the first hit. Note what it prints: the line number, not the passphrase — your secret never reaches stdout unless you ask for --json.

Where does that candidate list come from? Not from mnemonic — generating guesses is a job for John the Ripper. You know it as a password cracker; here it is only a candidate generator, and its --stdout mode computes no hashes and cracks nothing. Give it the roots you half-remember and the habits you actually use, and its mangling rules expand them. 

# the jumbo build: brew install john-jumbo | apt-get install john | pacman -S john
printf 'Satoshi\nhodl\nbitcoin\n' > roots.lst
cat > mangle.rules <<'RULES'
[List.Rules:Demo]
:
l
u
c
c $1
c $!
l $2 $0 $0 $9
RULES
john --config=mangle.rules --wordlist=roots.lst --rules=Demo --stdout
18 candidates from 3 roots: as-is, lowercased, upcased, capitalised,
+1, +!, +year. Stock rulesets (--rules=Jumbo) generate thousands more.

Then pipe it straight in — process substitution, so the list of guesses never touches disk: 

printf '<your 12 words>' | mnemonic xpub-search passphrase-of-xpub   --phrase-stdin --target-xpub <your xpub>   --passphrase-candidates-file <(john --config=mangle.rules --wordlist=roots.lst --rules=Demo --stdout)
match: candidate on line 4 derives the target xpub at m/84'/0'/0'

Line 4 is satoshi — the lowercase mangle of the “Satoshi” you would have typed. John generates, mnemonic verifies, and neither the guess list nor the winning passphrase is ever written to disk. Your own wallet, your own forgotten word.

“Which cosigner am I?”

A keyless multisig template engraves the wallet type — one plate serves thousands of wallets, and the keys are supplied at restore. But which key belongs in which slot? Guess wrong and you get a different wallet with no error. So give it the one thing you do have: an address you know is yours. 

printf '<your 12 words>' | mnemonic restore --from phrase=-   --md1 <template-md1> --account 0   --cosigner <xpub> --cosigner <xpub>   --search-address <an address you know is yours> --count 1
multisig wallet completed from template:
  first recv: bc1q4vxm2xewpdj2ycxyh9c4w923pjyl0e8dnf0y0gvwz2daxg36mecqhzarw0
  your seed completes cosigner slot @0

The cosigners went in unpositioned and in the wrong order. It searched the key→slot assignments for the one whose output script matches your address — and it will not guess: it returns an answer only after proving no second assignment also matches.

“I only wrote down the wallet-id”

The same search runs off the recorded wallet-id alone — no address needed. The template engraving prints one precisely so you can. 

printf '<your 12 words>' | mnemonic restore --from phrase=-   --md1 <template-md1> --account 0   --cosigner <xpub> --cosigner <xpub>   --expect-wallet-id 72d94d49b0aca695 --count 1
  first recv: bc1q4vxm2xewpdj2ycxyh9c4w923pjyl0e8dnf0y0gvwz2daxg36mecqhzarw0
✓ wallet-id (completed): 72d94d49b0aca695055b3de0a1f13bea
  your seed completes cosigner slot @0
It never silently guesses — and that is the point. It sizes the requirement to the search space and tells you the number it wants: for this 3-slot wallet, 10 hex characters proves the answer is unique. Supply less and it does not shrug and pick one — it shows its work:
72 (2 hex) refused — below the floor; a 1-byte prefix over any real space is a wall of matches that teaches nothing
72d9 … 72d94d49 several matches → lists the candidates and reconstructs none; exactly one match → completes, with a loud UNIQUENESS NOT PROVEN warning naming the bytes you gave and the bytes it wanted
72d94d49b0ac+ (10 hex) accepted — uniqueness proven, no caveat
A wrong id still returns ✗ NO MATCH and exit 4 — never a plausible wrong wallet. And a candidate list is deliberately not importable: rows carry an id, the key→slot assignment and an address, but no descriptor, so nothing downstream can act on a guess.

This changed. A short id used to be refused outright — which sounds safer and was not: it left an operator who recorded four hex with a dead end, and pushed them toward asserting cosigner positions by hand, which nothing verifies.
Short on id? Use the address instead — it is the better key anyway. If you wrote down fewer digits than it asks for, you are not stuck. Any known receive address of the wallet answers the same question with no prefix-length argument at all: 
printf '<your 12 words>' | mnemonic restore --from phrase=-   --md1 <template-md1> --account 0   --cosigner <xpub> --cosigner <xpub>   --search-address <a known receive address>
An address is matched on the full scriptPubKey, so unlike an id prefix it is collision-free — the tool's own help calls it “recommended over --expect-wallet-id”. It scans receive indices 0–19 by default; --search-addr-min / --search-addr-max widen the range and --search-chain reaches the change branch.

On your own wallet, bring the mk1 cards. The demo's cosigners are plain xpubs with no recorded origin, so --cosigner <xpub> completes it. A real engraved wallet usually records each cosigner's fingerprint and path on an mk1 card — and a bare xpub supplies neither (it decodes to fingerprint 00000000 and an empty origin), so the same command returns ✗ NO MATCH even when your id and address are perfectly correct. Pass the mk1 chunks to --cosigner instead. This is true in both modes: a scriptPubKey is origin-independent, but your own key's derivation path is still inferred from the cosigners' metadata, so --search-address does not rescue it.

One or the other — supplying both is now an error. --expect-wallet-id and --search-address are mutually exclusive and the tool refuses the combination by name. Before that it accepted both and silently ignored the address, which is why this page used to tell you to pair them. They pin different things — the address pins the key set, the id pins the labelling — and for sortedmulti that difference is moot anyway, because the script sorts keys at every index, so swapping two cosigners' labels yields the identical wallet.
What this cannot do yet. The passphrase search matches against an xpub rather than an address — recorded as open work rather than glossed over. Generating the candidate list is not on that list: that is John the Ripper's job, shown above, and not something the toolkit needs to reimplement.

When argv really is safe

A tool that only ever says no teaches people to route around it. On a single-user air-gapped machine, an amnesic Tails session, or an offline Blockstream satellite node there is no second user to read /proc, no network, and no history that outlives the session. The threat being modelled is not present — so the tool gets out of your way, and says so in the refusal itself: 

ms split --phrase "<your words>" -k 3 -n 5 --group-size 0 --allow-argv-secret
share 1 of 5:
ms13zereq3arxz33xqwgeswner6uet85ncm6sgsukqw9yykxzy
...
warning: stdout carries private key material (can spend) — redirect or encrypt

Exit 0, five shares — and note the other warnings do not go away. Opting out of one protection does not opt you out of the rest. The flag is deliberately greppable, so --allow-argv-secret in a script is something a reviewer can find. md, mk, mt and mnemonic all accept it, with the same meaning.

Already typed it before reading this? The refusal prints the cleanup, and the part people get wrong is this: match on the COMMAND, never on the secret — grepping your history for your own seed types it in a second time. 
zsh:  fc -W; sed -i '/\bms split\b/d' "$HISTFILE"; h=$HISTSIZE; HISTSIZE=0; HISTSIZE=$h; fc -R
bash: history -w; sed -i '/\bms split\b/d' "$HISTFILE"; history -c; history -r
fish: history clear-session
Run all the steps — the entry is still in the shell's memory, so editing the file alone changes nothing and the shell writes it back when you exit. And shred -u anything you pasted from.
A word on what this is. SeedHammer II engraves wallet backups into steel. The policies you build here are real BIP-388 wallet policies; the plate strings are real; the error correction is real. What's emulated is the machine — the screen, the buttons, the motion of the cutter.
