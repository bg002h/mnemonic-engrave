### C-2's new floor DOES catch the mis-parse mutation — traced, not assumed

The brief asked me to be strict here, because a golden generated by the same
flag-aware binary would recreate the defect one level up. It does not:

1. Step 9b generates the golden with **`md` 0.18.0, before the flag exists**,
   and commits it in its own commit. A binary with no `--unspendable` argument

   fact about 0.18.0's bytes.
2. The mutation is `"nums" → UnspendableKind::Liana` in Step 7's parser. Step 7
   specifies `#[arg(long, value_name = "KIND", default_value = "nums")]
   unspendable: String` — clap's `default_value` means **the omitted-flag case
   goes through the same string parser**. So the mutation moves the *default*
   too.

   asserts `out == expected`. Under the mutation the default emits
   `tr(UNSPENDABLE(liana),…)` while the golden holds
   `tr(50929b74c1a04954…,…)` → `assert_eq!` fails → **RED**.

Mutation (a) (swapped arms in Step 6) reaches the same assertion by the same
route. Step 9 now names the golden test for both, which is the half r0 said was
wrong. **C-2's remedy is structurally sound**, subject to M-f below.

## I-c — Task 2c schedules a fix for a defect this tree does not have: v8 is in the accepted version set, so the trigger is unreachable, and the prescribed fix site is wrong

Task 2c Step 1 (`:325`):

> write the failing test — a v8 chunk with a single correctable error; assert
> the corrected payload survives AND the exit distinguishes "unsupported
> version" from "could not correct".

**The trigger does not exist at `25acb33c`.** `Header::is_supported_version`
(`crates/md-codec/src/header.rs:36-38`) returns true for
`WF_REDESIGN_VERSION` **and** `WF_UNSPENDABLE_VERSION` — the accepted set is
`{4, 8}`, grown by stage 1b, and `ChunkHeader::read` (`chunk.rs:70-73`) uses the
same predicate.

MEASURED, end to end, with the tree's own binary:

```
$ md encode 'tr(UNSPENDABLE(liana),{multi_a(2,@0/48'/0'/0'/3'/<0;1>/*,…),and_v(v:pk(@3/…),older(26280))})'
md1crfdsssj6tvyywtfdssj5kjmpp9ewqqvpu2gpzrye54hqqqpn2svvcyaf6t38n5x

$ md repair md1qrfdsssj6tvyywtfdssj5kjmpp9ewqqvpu2gpzrye54hqqqpn2svvcyaf6t38n5x
# Repair report
#   md1 chunk 0: 1 correction at position 0: 'q' -> 'c'
md1crfdsssj6tvyywtfdssj5kjmpp9ewqqvpu2gpzrye54hqqqpn2svvcyaf6t38n5x
exit=5
```

A v8 chunk with a single correctable BCH error **already** keeps its correction
and exits 5. There is no "unsupported wire version" outcome to distinguish, so
Step 1's test cannot be made to fail and Step 3 (*"prove the test fails without
the fix"*) cannot be executed.

The spec row the task cites says why: `SPEC_liana_unspendable_internal_key.md:586`
is scoped to **`md repair`, older binary** — a *released* md whose accepted set
is `{4}`. That is a forward-compatibility concern about binaries that are not
this tree.

**The fix site is also wrong.** Task 2c Step 2 says *"fix `repair.rs` to carry
`details` through."* It cannot: the details are destroyed **inside md-codec**,
not in md-cli. `decode_with_correction` (`chunk.rs:532`) accumulates
`all_details`, then discards them at the two `?` operators that finish the
function — `chunk.rs:659` (`decode_md1_string(&corrected_strings[0])?`) and
`chunk.rs:666` (`reassemble(&corrected_refs)?`). `repair.rs:88-96` only ever
sees `Err(e)`. The fix requires an md-codec API change (a details-carrying
error, or a second entry point) — which the plan's `File Structure` section does
not list, and which sits awkwardly beside *"this stage adds no wire behaviour"*.

**The reachable half, constructed.** The *mitigation* clause of `SPEC:586`
(*"never discard a correction that succeeded"*) IS reachable today, just not via
a wire version. MEASURED on a 3-chunk v8 set with chunk 0 corrupted and chunk 2
withheld:

```
$ md repair <chunk0-with-1-error> <chunk1>
md: repair: chunk set incomplete: got 2 chunks, expected 3
exit=2
```

Chunk 0's BCH correction succeeded and was thrown away, and exit 2 is the
atomic-fail code — indistinguishable from "could not correct". That is the real
defect, it is version-independent, and it is what Task 2c should target.

**Remedy.** Either retarget Task 2c at the reachable case above (and state the
md-codec change in `File Structure`), or move §8.9's row to a later stage **in
the spec** with the move recorded in Task 7 — r0's I-2 offered both, and the
fold took a third option that does not execute.
