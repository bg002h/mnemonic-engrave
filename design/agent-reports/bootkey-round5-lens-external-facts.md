## External-facts verification — pico2-bootkey-rehearsal / FIRMWARE-QUICKSTART.txt

Scope: FIRMWARE-QUICKSTART.txt (first review), RUNBOOK_custom_boot_key.md, pico2-bootkey-rehearsal.sh, sign-firmware.sh, cross-checked against the actual RP2350 bootrom source (`raspberrypi/pico-bootrom-rp2350`, cloned), the pinned sweet-b fork (`raspberrypi/sweet-b@824183c`), the pico-sdk register header (`hardware/regs/otp_data.h`), picotool's own source (`raspberrypi/picotool`), and an empirical openssl test — not our own docs/scripts, per the assigned lens.

### The six items, settled

**1. High-s rejection — REFUTED, plus empirical measurement.**
Checked the actual verify path: `pico-bootrom-rp2350/src/main/arm/arm8_sig.c` (`s_arm8_verify_signature_secp256k1`) calls straight into `sb_sw_verify_signature` in the **pinned submodule commit** `raspberrypi/sweet-b@824183c4836281e5b7d4f2d2e6d547b34d1aab81` (`src/sb_sw_lib.c`). The only scalar check is `sb_sw_scalar_validate`: `0 < k < n`. Grepped the whole file for `half`, `>> 1`, `canonic`, `malle`, `low_s` — zero hits. **There is no low-s/canonicality check anywhere in the RP2350 secure-boot signature path.** A high-s signature verifies identically to a low-s one.
Empirically: 500 openssl secp256k1 ECDSA signatures over random messages → 266 high-s (53.2%), consistent with the ~50% theoretical rate for an unconstrained nonce.
**Conclusion: the runbook's step-6 "if it does, roughly half of all signatures fail this way" is not a live risk — it's settled and false.** A boot failure after step 3's readback passes is never a high-s artifact.

**2. BOOTSEL fallback on a rejected/absent image — CONFIRMED.**
`varm_blocks.c`: a failed signature check sets `parsed_block->verified = hx_false()` and falls through to `verify_done` — a graceful "not verified" marker, not a halt/crash/retry-loop. `varm_flash_boot.c` comments confirm the caller's behavior on this: *"if that returns, we're falling through to next bootable partition, or flash boot failed"*. `varm_boot_path.c` (~line 918): after `s_varm_crit_ram_trash_try_flash_boot(...)` returns with no image booted, execution falls through **unconditionally** to `debug_label(stepx_nsboot_preamble)` and enters nsboot (BOOTSEL/USB), gated only by the `DISABLE_BOOTSEL_*` OTP bits — which `driver/otp/` never writes (already established). Phase 5b's "did it reappear as a BOOTSEL drive" acceptance signal is architecturally correct.

**3. OTP write semantics — CONFIRMED, with one added nuance.**
`picotool/main.cpp`: `-s`/`--set-bits` is literally `settings.otp.value |= old_raw_value` (host-side OR-in) — matches the doc's description exactly. Independent of that flag, the **device itself** (`pico-bootrom-rp2350/src/main/arm/varm_otp.c`, `s_varm_api_hx_otp_access`) refuses any write that would clear a bit — `if (current_val & ~full_val) rc = BOOTROM_ERROR_UNSUPPORTED_MODIFICATION` — before the fuse-program call, for both `otp set` and `otp load`. Locked-page writes fail the same way with `BOOTROM_ERROR_NOT_PERMITTED`, checked before any program call. **Added nuance not previously stated anywhere:** a multi-row write (e.g. the 16-row boot-key load) is a per-row loop in the bootrom — each row is burned immediately as it passes its own check, so a mid-command failure leaves the earlier rows in that command already (irreversibly) written and the rest untouched. This doesn't undermine anything: since writes can only set bits, never corrupt, the result is always "some rows correctly hold the intended value, the rest still blank" — never ambiguous or unreadable — which is exactly why the runbook's mandatory full-16-row `--sh2-verify-slot` readback (not a partial check) is the right and sufficient gate. Not a finding, just confirmation the design already assumes the right thing.

**4. KEY_VALID/KEY_INVALID semantics — CONFIRMED**, and better than expected: `hardware/regs/otp_data.h` (pico-sdk, generated from the RP2350 datasheet) documents this natively: *"A KEY_VALID bit is ignored if the corresponding KEY_INVALID bit is set,"* multi-key support is explicit — *"The bootrom will check signatures against all valid boot keys"* — and Raspberry Pi's own text says verbatim: *"Verify keys after programming, before setting the KEY_VALID bits — a boot key with uncorrectable ECC faults will render your device unbootable if secure boot is enabled."* That is precisely the runbook's step-2→3 discipline, now confirmed as vendor-recommended, not just self-consistent. `pico-bootrom-rp2350/varm_blocks.c` (`s_varm_crit_is_signing_key_match`) independently confirms the bootrom loops `k=0..3` checking each valid slot, so simultaneous multi-key validity is real, exercised hardware behavior, not an inference from the fork's Go code.

**5. Slot count/layout/byte order — CONFIRMED from the bootrom itself, independent of the fork.**
`otp_data.h`: `BOOTKEY0_0_ROW=0x080`, `BOOTKEY1_0_ROW=0x090` (spacing 16); `BOOT_FLAGS1_ROW=0x04b`, `KEY_VALID` bits 0-3, `KEY_INVALID` LSB 8; redundancy confirmed as CRIT1 R1..R7 (8 copies, rows 0x040-0x047) and BOOT_FLAGS1 R1/R2 (3 copies, 0x04b-0x04d) — exactly the settled facts. Byte order: in `s_varm_crit_is_signing_key_match`, the comparison reads `buffer_val = *(uint16_t*)&digest_buffer.bytes[i]` (little-endian CPU) against `otp_key_hword` from row `k*16 + i/2`, for `i` stepping 0,2,4…30 — i.e. row *n*'s low byte holds hash byte 2n, high byte holds hash byte 2n+1, rows read in ascending order reproduce the hash in original byte order. This is exactly the reassembly `read_slot()` performs, now validated against the real verification code, not just the fork's own writer.

**6. `(UNLOCKED)` claim — CONFIRMED** directly: `platform_sh2.go:710-738` `isSecureBootEnabled()` returns `enabled && ours && nvalid == 1`; `gui/gui.go:2717-2719` appends the suffix exactly when `FeatureSecureBoot` is absent. A second valid key makes `nvalid==2`, forcing the suffix. No daylight between the doc's claim and the code.

### Findings

**Important — RUNBOOK_custom_boot_key.md:292-295 (mirrored conceptually, though not verbatim, in the quickstart's "signing problem" framing at FIRMWARE-QUICKSTART.txt:143-144): the step-6 failure-diagnosis text presents a refutable, now-refuted hypothesis as an open risk, at the single most stressful diagnostic moment in the whole procedure.**
- Finding: *"Whether the RP2350 bootrom rejects high-`s` signatures is not verifiable from this repo; if it does, roughly half of all signatures fail this way…"* — this has been flagged as unverified since round 0 (5 review rounds) and was resolvable the entire time from Raspberry Pi's own public bootrom source. It is now settled: **the bootrom performs no such check.** A post-step-3 boot failure is never a high-s artifact.
- Concrete failure scenario: operator completes both irreversible OTP writes, flashes, board doesn't boot. They read the runbook's own text, which explicitly primes "an intermittent pattern across re-signs points here [to high-s]." They re-sign 2-3 times (harmless, since re-signing is free — no slot risk), see no change (because it was never the cause), and either give up misdiagnosing a real defect (bad build, wrong image, an actual picosign/miniscript bug) as "bad luck with s," or waste real time chasing a phantom before looking at the actual cause.
- Recommended fix: replace the "not verifiable / if it does" language with the settled fact: *"The RP2350 bootrom (verified against `raspberrypi/pico-bootrom-rp2350` and the pinned `sweet-b` fork) performs no ECDSA canonicality/high-s check — signature s-value is never the cause of a boot failure here. If step 3 passed and the image still doesn't boot, look at genuine signing/build defects (wrong key, corrupted UF2, metadata-block count, picosign ordering) instead."* This is a net simplification, not new caution — it removes a false lead rather than adding one.

No Critical findings. No other Important findings survived: every other externally-checkable claim in the runbook and the (newly reviewed) FIRMWARE-QUICKSTART.txt — BOOTSEL fallback, OTP write/lock semantics, KEY_VALID/INVALID behavior and multi-key support, slot layout and byte order, and the `(UNLOCKED)` display logic — is CONFIRMED against primary sources (Raspberry Pi's own bootrom source and register definitions, picotool's own source, and the fork's own signing-decision code), not merely internally consistent with our own prior claims. FIRMWARE-QUICKSTART.txt itself introduces no new external-fact claims beyond what the runbook already states, and its condensed high-s-adjacent text ("re-sign and re-flash… DO NOT burn another slot") happens to already avoid repeating the specific refuted theory, so it does not need the same correction — only the runbook does, and the finding above is written to fix the source of the claim.

**Verdict: no Critical/bricking-relevant external-fact defect found; one Important stale/refuted claim (the high-s hypothesis) should be corrected to the now-settled fact before the SH2 is touched, and every other externally-checkable safety claim in these artifacts — including three (BOOTSEL fallback, byte order, multi-key support) that had never been checked against a primary source before this pass — is CONFIRMED.**
