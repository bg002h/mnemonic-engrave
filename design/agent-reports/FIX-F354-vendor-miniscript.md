## 1. What was wrong

`vendor/miniscript` held rev `95fdd1c5`; `Cargo.toml`/`Cargo.lock` pin
`ff4732e5` (rust-miniscript PR #953, *"descriptor: fix Taproot tree descriptor
formatting"*). Pre-existing since `33c215a5` (2026-06-24).

Only the `--offline` vendored path uses that tree, and that is what the
reproducible musl **release** binary is built from. Every networked build
resolved `ff4732e5` from git and was correct. Meanwhile the repo had already
been changed to assume #953 was present — `restore.rs`'s
`ensure_taptree_depth_le_one` was lifted to `ensure_taptree_wellformed`, and two
cells in `tests/cli_restore_taproot.rs` were flipped from refusal to
reconstruction — so the release binary compiled the broken formatter **with the
guard that protected against it already removed**.

## 4. The two flipped taproot tests — and proof they can fail

`crates/mnemonic-toolkit/tests/cli_restore_taproot.rs`:
`left_heavy_3leaf_tr_restores_depth2` and
`right_spine_3leaf_tr_also_restores_depth2`.

Against the networked build they pass, but that build never touches `vendor/`.
So they were run **against the vendored tree**: empty `CARGO_HOME` (so
`~/.cargo/git` cannot supply the rev), `--offline --locked`, 3-block source
replacement.

| vendored tree | `left_heavy` | `right_spine` | summary |
|---|---|---|---|
| **old** `588898e0` | **FAIL** | PASS | 21 tests run: 20 passed, **1 failed** |
| **new** `8f6bc3a9` | PASS | PASS | 21 tests run: 21 passed, 0 skipped |

The failure, verbatim:

```
error: --md1 descriptor parse: taptree branch must have 2 children, but found 1
```

The old formatter prints `{{a,b},c}` as `{{a,b,c}}`, which its own parser then
rejects.

**`right_spine` passes on BOTH revs** — exactly as the test's own comment
predicts, since a right-spine tree printed correctly even on the old pin.
`left_heavy` is the discriminating cell. A test that passes in both worlds is
not a test, and here one of the two genuinely is not; it is kept, correctly, as
a chirality control.

**A false GREEN on the way, worth recording.** The first old-tree run reported
21/21 pass. It had compiled **nothing** — `Compiling miniscript` appeared 0
times and cargo finished in 0.06s. **Cargo treats a vendored source as immutable
under a fixed package-id**, so it does not notice the tree changing underneath
it. Only after `cargo clean -p miniscript` (confirmed by `Compiling miniscript`
= 1 on both legs) did the real result appear. Checking that the command actually
ran is what caught it.

**Severity is narrower than feared, and this matters.** The observed failure mode
is **fail-closed**: restore refuses at descriptor parse (exit 1). A valid
depth-≥2 taproot backup was **unrestorable** by the release binary, not silently
mis-restored to a wrong address. Still funds-relevant — a restore tool that
cannot read a faithful backup — but it is not a wrong-address defect.

## 6. The gate — `ci/repro/vendor-freshness.sh`

### The finding that shaped the design

The brief proposed verifying `.cargo-checksum.json` against disk. **Measured
first, and it would not have caught F-354:** on the defective tree that check is
**168 crates, 7479 files, 0 mismatches**. `cargo vendor` wrote the manifest from
the same wrong rev it wrote the files from, so the tree is internally
self-consistent. Nothing in a vendored git source records its rev
(no `.cargo_vcs_info.json`, no rev string anywhere).

Checksums catch corruption and hand-edits. Only **provenance** catches "vendored
from the wrong source". A checksum-only hardening would have shipped a gate that
still could not see the defect it was written for.

### A second measurement that made the gap precise

Exactly **one of 168 crates has no offline provenance anchor** — and it is
`miniscript`. For every crates.io crate, `.cargo-checksum.json`'s `package` is
the sha256 of the published `.crate` and equals `Cargo.lock`'s `checksum`
(167/167). A git source has no published tarball, so both are `null`. The single
unanchored crate is the one that drifted.

### What the gate now does

Four checks, ascending cost, all offline; ~0.2s for 7479 files, so **nothing is
sampled**.

1. **Resolution** — unchanged.
2. **Integrity** — every file vs its recorded sha256.
3. **Registry provenance** — `package` vs `Cargo.lock` `checksum`, **and** the
   set of unanchored crates must be exactly the grounded one.
4. **Git-fork provenance** — the hole (3) cannot reach, anchored against a
   digest grounded by hand against upstream.

### Mutation tests — both directions, from a clean 0-finding baseline

| | mutation | result |
|---|---|---|
| M1 | append one byte to `vendor/bitcoin/src/lib.rs` | **RED** exit 1, names the file + both digests. **Check (1) still reported OK** — the old gate's blindness, demonstrated |
| M2 | restore it (`git diff` clean) | exit 0, **stderr empty** |
| M3 | **restore the actual F-354 tree** | **RED** exit 1 at check (4). Check (1) OK, check (2) silent — the tree is self-consistent |
| M4 | restore the fixed tree | exit 0, **stderr empty** |
| M5 | tamper `vendor/bitcoin`'s `package` digest | **RED — but at check (1)** |
| M6 | pretend a new unanchored source appeared | **RED**, names it |
| M7 | pretend the pin moved with no re-grounding | **RED**, with re-ground instructions |

**M3 is the regression test for the defect itself**, and it is the one that
justifies the work: on the exact tree that shipped for two months, the original
gate says OK and the new one says no.

**M5 changed a claim.** Cargo already validates the registry digest during
resolution (`checksum for `bitcoin v0.32.8` changed between lock files`), so
check (3)'s digest comparison is **redundant with cargo**. The header was
corrected to say so, and (3) is kept for the **unanchored-set assertion**, which
cargo does not make — a new git or path dependency that no digest can vouch for
is precisely the shape F-354 arrived in.

**Quiet on non-defects:** clean tree is exit 0 with empty stderr.

### Stated blind spots (in the script's own header)

- Checks (2)–(3) prove the tree matches **what `cargo vendor` wrote**, not that
  what it wrote **came from the pinned rev**. For crates.io crates that gap is
  closed by the published-tarball digest; for the git fork there is no such
  digest.
- **Check (4) is trust-on-first-use.** It proves the tree has not *changed*
  since a human grounded it against GitHub; it cannot itself prove the grounding
  was right. The header carries the re-grounding command, and M7 shows the gate
  REDs with instructions when the pin moves — it neither passes silently nor
  fails forever.
- Nothing here re-proves bit-for-bit reproducibility; that stays with
  `repro-drift.yml` and the release `repro` gate.
