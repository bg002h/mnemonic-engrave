## F-672

**Reproduced first** with the report's command: `md descriptor --template 'tr(UNSPENDABLE(liana),{multi_a(2,@0..@2),and_v(v:pk(@3),older(26280))})' --key @i=[fp/48'/1'/k'/3']tpub… --network regtest` gave the evidence's descriptor byte for byte (checksum `#v3zqvwu5`). Its leaves were `xpub6DXu…` and its internal key was `tpubD6Nz…`.

**Cause.** `to_miniscript.rs::assemble_origin_and_xkey` built every `@N` xpub through `xpub_from_tlv_bytes`, which hard-codes `NetworkKind::Main`. The `_with_network` entry points threaded `network` only into the Liana internal key. Their doc comment said the network was "otherwise unused". The existing testnet test (`liana_to_miniscript.rs::a_tpub_wallet_renders_a_tpub_internal_key`) asserted only the internal key, which is how the defect got past it.

**Fix.** `assemble_origin_and_xkey` and the two key builders now take `network`, and every key gets `NetworkKind::from(network)`. The network-less entry points still pass `Bitcoin`. All changed functions are private, so the public API is unchanged.

**Other `--network` commands.**
- `md address`: it prints only addresses, and the HRP already followed the network. It was unaffected, and a test pins it (`bcrt1p`).
- `md compose`: it has no `--network` flag.
- `md decompose`: it echoes the input keys, so its key output was correct. However, `--emit commands` printed a route-1 `md encode --key @i=tpub…` line with no `--network`. Running that recipe as printed failed with `expected mainnet xpub version 0488B21E, got 043587CF`. **Fixed**: route 1 now appends `--network <net>` on test networks. Route 2 carries no keys, and mainnet output is unchanged.
- `md encode`/`md verify`: they parse keys and do not render them.

**Tests (all red before the fix).**
- md-codec `tests/network_version_bytes.rs`:
  - Vector test: four corpus vectors (kind 0 `keyed_compose_tr_two_path_nums`, kind 1 `keyed_tr_liana_kofn_recovery`, real internal key `keyed_tr_with_leaf`, wsh `keyed_wsh_multi_2of3`) × 3 test networks × {multipath, chain 0, chain 1}, each compared to a golden.
  - The goldens are derived outside md by `tests/fixtures/network/derive.py`: take the mainnet render, base58-decode each xpub, swap the version to `043587CF`, re-encode, and recompute the BIP-380 checksum. As a cross-check, the kind-1 internal key it predicts equals what the unfixed binary already printed under regtest.

M4, the network-less entry passing Testnet, now turns it red.

## Concerns

1. **The brief asked for `md compose` to show the new Core verdict, and it cannot.** Compose outputs a keyless template, and design §1 (a2) forbids a template from claiming an import. The verdict is visible on `md descriptor`, as shown above. Changing this would be a design change, not a follow-up.
2. **`measured_at` is 2026-09-24.** The vendor script's rule takes the engrave committer date in UTC, and `4db2f17d` was committed after midnight UTC. The measurements themselves were taken on 2026-09-23 local time.
3. **The key covers any `older` value.** The SkeletonKey abstracts lock values (`older-blocks#1`), so the Core cells apply to kofn/tiered-recovery at any block-based `older`, not only 26280. That is the existing design contract, and no Core rule reads lock values.
4. **A decompose message names the wrong network.** On a mismatch it prints "--network says testnet" even when the user passed regtest, because it prints the NetworkKind. This is pre-existing and was not changed.
5. **The engrave worktree has an uncommitted change I did not make:** `design/SPEC_wallet_policy_composer.md`. I left it untouched and unstaged.
6. **Not vendored:** the same run's Liana v15.0 results (`live/liana-out.jsonl`, `regtest/liana-regtest-out.jsonl`), which are outside F-673's scope.
