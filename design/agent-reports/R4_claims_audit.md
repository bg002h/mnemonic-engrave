## SEVERITY — "the transcript ran `mk encode` 33 times... now runs it 2"

**What's actually true, machine-measured by executing the real script both ways:**

- **Pre-fix (`85cf6c7`, before `01697a1`): 35 real `mk encode` subprocess invocations**, not 33. Breakdown, confirmed by both an `mk`-wrapper call-log and independent `bash -x` tracing: 1 (§5/6 single-card demo, `run "$MK" encode ...` at old script line 131) + 1 (§5/6 stub cross-check, `MK_STUB=$("$MK" encode ...)` at old line 154) + 11 (§7's per-key card loop, old line 189) + 11 (§7b's card-index chunk-count loop, old line 235) + 11 (§7b's card-index string-read loop, old line 242) = **35**.
- **Post-fix (current `master`): 3 real invocations**, not 2. Breakdown: 1 (§5/6 demo) + 1 (§5/6 cross-check) + 1 (§7's single batch `mk encode --keys` call) = **3**.
- The commit's own internal accounting — "eleven cards in section 7, plus TWENTY-TWO in the card-index step... = 33" — is arithmetically self-consistent (11+22=33) and correctly describes **only §7/§7b**. The error is that the top-level claim ("**the transcript** ran mk encode 33 times... now runs it 2") is about the *whole script*, and both the before-count and the after-count silently omit the two §5/6 calls (the single-card demo + the stub cross-check) that exist unchanged on both sides of the fix. Those 2 calls are present in **both** the old and new script, so they cancel in the *delta* (33→2 undercounts by exactly 2 on the "before" side and by exactly 1 on the "after" side — not a symmetric omission, because the "before" §7 loop coincidentally shares one of its 11 iterations' key with the §5/6 demo's own xpub, while the "after" batch call is a single call regardless).
- **Net effect on the qualitative claim ("collapses dramatically") is unaffected** — 35→3 is still an ~92% reduction, comparable in shape to the claimed 33→2. But the **exact numbers are wrong on both sides**, in **three places**: the mnemonic-engrave commit message `01697a1` (title and body), `design/FOLLOWUPS.md`'s F-223 entry ("Closes at 33 -> 2"), and commit `438f86f`'s message ("Closes at 33 -> 2"). This is exactly the class of error the project's own standing lesson (`records are wronger than code`) warns about, and it recurred inside the very entry (F-223) that was already flagged in this same cycle for one prior wrong measurement ("~33 commands to ~3" vs. the corrected "33 -> 2" — the corrected number is *itself* wrong).
- **Severity: Important.** It is a false claim recorded in `design/FOLLOWUPS.md` (an Important-or-above artifact per the audit brief's own rule), it is the exact measurement that motivated and named this cycle (F-223's "collapse the pathological wallet's key-card build" framing), and it was stated with confidence as a correction to an earlier wrong number — making it a second wrong number layered on the first, silently. It is not Critical: no funds/security/wire-format consequence, the byte-identity and card-count invariants that matter operationally (30 mk1 strings, 11 cards) are independently confirmed correct, and the qualitative "big collapse" conclusion still holds.
