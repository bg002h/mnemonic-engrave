## F-683 — ms `--separator` help

**Cause.** No value enum existed. `--separator` on `encode`, `split` and `hashlock` used a
hand-written doc comment (`Separator: space|hyphen|comma (keyword) or the literal " "|-|, .`)
plus the free-function parser `format::parse_separator`, which since §6c refuses hyphen/comma.
The two lived apart, so they drifted. `gui-schema` listed the flag as `text` with no choices.

**Fix, at the source.** In `crates/ms-cli/src/format.rs`:
- `pub const SEPARATORS: &[(&str, char)] = &[("space", ' ')]` is now the only list.
- `parse_separator` accepts each keyword in the list and its literal char. Retired values keep
  their existing error text, byte for byte.
- A new `SeparatorParser` (a `clap::builder::TypedValueParser`) delegates parsing to
  `parse_separator` and returns the list's keywords from `possible_values()`.
All three verbs now use `value_parser = crate::format::SeparatorParser`, and their doc comments
say `space` only and that old hyphen/comma cards still decode. Intake is unchanged.

**New `--help`** (encode and split. hashlock is the same, and keeps its "BOUND TO THE SHARED PARSER" paragraph):
```
      --separator <SEPARATOR>
          Separator between groups: `space` (or the literal " "). SPEC §5. `hyphen` and `comma` are no longer emitted (§6c); a card already grouped with them still decodes
          [default: space]
          [possible values: space]
```

**`gui-schema` change, for the GUI's next pin bump.** For `--separator` on exactly `encode`,
`hashlock` and `split`, the schema changes from `"kind": "text", "choices": null` to
`"kind": "dropdown", "choices": ["space"]`. Nothing else changes: `name` and `required: false`
are the same, and the flag count is still 70. Measured by diffing `ms gui-schema` output before and after.
If the GUI imports `choices`, it gets a one-entry dropdown, which matches what it already
shows after dropping hyphen and comma.

**Test.** New `crates/ms-cli/tests/f683_separator_help_offers_what_ms_accepts.rs`. It fails
before the fix (2 of 3 red) and passes after. It reads every `--separator` verb from
`gui-schema` (asserting the set is encode/hashlock/split), checks that `choices == ["space"]`,
runs every offered value on each verb (exit 0), and checks that the help shows
`[possible values: space]` and no retired value. A unit test `every_offered_separator_parses`
covers the `SEPARATORS` → `parse_separator` link.

**Gates (all run):** `cargo nextest run --locked --workspace`: 628 passed, 11 skipped. Pinned
clippy 1.85.0 (`clippy 0.1.85`, toolchain bin first on PATH) `--workspace --all-targets -D

## F-686 — `restore --help` depth-≥2 claim

**Source.** The claim was in the `--md1` doc comment in `crates/mnemonic-toolkit/src/cmd/restore.rs`,
which also generates the man page. It now reads: "...plus general taproot policies, in a tap tree of any
depth; the @-in-both shape (trunk key also a leaf key) and `sortedmulti_a` anywhere but as the
single leaf are refused." The second refusal was always enforced
(`subtree_contains_sortedmulti_a`) but the help never named it.

**The same claim elsewhere.**
- CLI manual `docs/manual/src/40-cli-reference/41-mnemonic.md`: fixed in 3 places (the intro
  paragraph, the `--md1` flag row, and the multisig Scope paragraph). Each "depth-1 two-leaf" or
  "single-leaf/depth-1" limit became "any depth", and the depth-≥2 refusal was removed.
- Man page: clap-generated from the doc comment. `gen-man` output checked: `mnemonic-restore.1`
  contains "tap tree of any depth" and no longer contains "taproot are refused".
- Help goldens: no committed golden contains this text (grepped the repo). The Examples golden
  regenerates unchanged.
- Stale internal comments with the same claim were fixed: `restore.rs` (the `TaprootRestore` enum doc,
  the `classify_taproot_restore` doc, and the step-3 comment), the `cli_restore_taproot.rs` module doc,
  and the `bitcoind_differential.rs` corpus doc.
- Changelog: a short F-686 entry under `[Unreleased]`.

**Real run** (worktree build and the 0.104.0 release binary gave the same result). Each run was
`bundle --descriptor` → `restore --network mainnet --md1 …` → compare with
`export-wallet --format bitcoin-core-addresses --count 1`:
- `tr(<NUMS H hex>,{{pk(K0),pk(K1)},pk(K2)})` (depth 2): restore exit 0. First recv
  `bc1p73fltnsnc46hgx9dkus48k9c9ray8hqpjkmqthtdd7ppr0kc0y6q0hfp7w`, equal to the export's `addr()`.
- `tr(K0,{{pk(K1),pk(K2)},pk(K3)})` (non-NUMS trunk, depth 2): restore exit 0. First recv
  `bc1pk2thw4z56v8dn8mhs2f2dm0m42dtwytxvf4x23ghx0cue2mmhf7qfln039`, equal to the export's.
  This is what backs changing the non-NUMS doc from "single-leaf/depth-1" to "any depth".

**Test.** New `restore_help_says_depth2_taproot_restores` in `tests/cli_restore_taproot.rs`. It was
