## 1. Verdict

**RED — 1 Critical, 2 Important.**

The **pre-block `syncArmed` call is correct and is the right fix for F-106.** I
reproduced its effect independently, on three different shapes, and it is
monotonically safe: it does not change the *set* of clock stamps, only their
timing, and only ever **earlier** — so it can make the window fire sooner but
never later.

What is RED is the **evidence**, and the **claim attached to the second call**.

## 2. THE PRIMARY QUESTION: the post-block call is **NOT load-bearing**

### Answer

**Not load-bearing.** The post-block `syncArmed` advances the observation of an
*asynchronous* (engrave-goroutine) arm edge by **at most one inner-loop
turnaround** — never by a wakeup. That is the categorical difference from
F-106, where the missed observation cost a full wakeup (three minutes). It is
not literally dead code — it does change one tick's branch selection — but it
does not carry any §10.2.4 guarantee, and the assertion in
`/scratch/code/shibboleth/seedhammer-f106/gui/run_flow.go:195-198` that "only
this call sees it" is **false**.

### Evidence — structural

`run_flow.go`'s inner loop has exactly one blocking call, `pl.AppendEvents`.
Between the **post-block** sample point and the **next iteration's pre-block**
sample point there is **no blocking call at all** — only the decision block,
`ctx.Reset()`, `ctx.Router.Events`, the `wipeNowHook` check, and at most one
flow frame:

- `a.idle.active == true` → the loop `continue`s at the 40 ms saver throttle
  (or the 1 s warning throttle) **without returning control to the flow**, so
  the next pre-block call runs ~40 ms later;
- `a.idle.active == false` → the loop `break`s, the flow draws exactly one
  frame, and the next pre-block call runs immediately after it.

So the author's hypothesised discriminating case — *"a park with no frame drawn
between a cut-end edge and the deadline"* — **does not exist**. When no frame is
drawn, the loop is in the 40 ms saver `continue`, which runs the pre-block call
every 40 ms. `EngraveScreen.Engrave`
(`/scratch/code/shibboleth/seedhammer-f106/gui/gui.go:2766-2775`) draws a frame
per loop iteration *and* sets `ctx.WakeupAt(now + 500ms)` while the job is
running, so the wakeup is ≤ 500 ms for the whole duration a job can be running.

### Evidence — measured

**(a) Whole-suite mutation.** Literal deletion (`armed := syncArmed(now)` →
`armed := a.armed`), full `./gui/` suite:

```
ok  	seedhammer.com/gui	38.349s
```

Green. **Nothing in the repository pins this line** — including
`TestRunPostCutWindowRestartsFromCutEnd`
(`/scratch/code/shibboleth/seedhammer-f106/gui/run_flow_test.go:511`), which is
the purpose-built §10.2.4 row-2 cut-end test and *does* exercise a genuine
mid-park edge (it flips `job.status.State` from inside `p.onDirty`, i.e. from
inside the screensaver park).

**(b) A real cut ending mid-park.** I built the case the design says the harness
"cannot currently express": `p.engraver = newEngraver()` so the job actually
runs, a spline that enters and sleeps 90 s inside the bubble, EngraveScreen's
500 ms poll modelled, and a `wakePlatform` variant whose `AppendEvents` also
selects on `p.wakeups` — the shape
`/scratch/code/shibboleth/seedhammer-f106/cmd/controller/platform_sh2.go:378-393`
actually has. Cut ends at `1m30.1s`; measured interval from cut end to warning
(want `3m0s`):

| variant | `deadlinePlatform` (no `pl.Wakeup`) | `pl.Wakeup` modelled (hardware shape) |
| --- | --- | --- |
| **both calls (the fix)** | 3m0.5s | 3m0.5s |
| **post-block deleted** | 3m0.0s | 3m0.5s |
| **pre-block deleted** | 3m0.0s | 3m0.0s |

Maximum divergence **500 ms** — one poll interval. In one row the fix is
*later* than the mutant, which is the pre-block stamp shifting the observation
by a tick. Nothing here resembles a doubling.

### What deleting it actually costs

On the single tick where an asynchronous edge first becomes observable, the
branch selection uses a stale `armed`: the loop draws **one screensaver frame
instead of one warning frame** and swallows that tick's events
(`Router.Events` is gated on `!a.idle.active`). The next iteration's pre-block
call resets the clock and clears `a.idle.active`, and the flow resumes. Never a
doubled window.

### Recommendation

Either is defensible; **shipping it with the current comment is not.**

- **Keep it** (my preference) — it is a genuine one-turnaround latency
  reduction and it keeps the branch decision consistent with reality on the tick
  an async edge lands. But the comment must be rewritten to say exactly that,
  and the design must stop calling it load-bearing (see **I1**).
- **Delete it** — then the replacement **must be `armed := a.armed`**, never
  `armed := ctx.wipe.armed()`. I measured the latter: a fresh sample without the
  stamp lets the warning branch be entered on a tick whose `a.idle.start` is
  still the *old* clock — the warning drew at `3m0s`, the instant of the arm
  edge, with no fresh window, and would have wiped 30 s later. Worth naming in
  the design as a trap, because it is one character away from the baseline's own
  `armed := ctx.wipe.armed()` line.

## 3. Findings

### C1 — CRITICAL: `TestArmEdgeDuringTheParkStillStartsAFreshWindow` is a false PASS; it never runs an engrave job

`/scratch/code/shibboleth/seedhammer-f106/gui/idle_late_arm_edge_test.go:97-162`

`newDeadlinePlatform()` never sets `p.engraver`, and
`testPlatform.Engraver` (`gui/gui_test.go:448-451`) returns
`errors.New("engraver unavailable")` when it is nil. So `runEngraving` fails at
its **first statement** (`gui/engraver.go:155`) and the job dies immediately.
Instrumented trace of the test's own scenario:

```
PRE   t=0s     jobState=0 splineEntered=false armed=true  start=0s
POST  t=2s     jobState=0 splineEntered=false armed=true  start=0s
FLOW  job.Start() at 2s -> state=1
PRE   t=2s     jobState=1 splineEntered=false armed=false start=0s
POST  t=3m0s   jobState=4 err="engraver unavailable" splineEntered=false armed=true start=3m0s
FLOW  about to close(cutting) at 3m0s; jobState=4 splineEntered=false
RESULT unarmedAt=3m0s warnAt=6m0s delta=3m0s splineEntered=false finalState=4 err="engraver unavailable"
```

- `splineEntered=false` — the `<-cutting` closure is **never entered**.
- `jobState=4` is `engraveFailed`. `close(cutting)` is a no-op on a dead job.
- The arm edge the test measures is `engraveRunning → engraveFailed`, i.e. an
  instant startup failure observed at the next wakeup — **not a cut end**.
- The test passes by coincidence: the flow's very next frame after the arm edge
  is the one that runs `close(cutting)`, so `warnAt - unarmedAt` lands on
  `idleTimeout` exactly.
- Note `warnAt = 6m0s` against a session start of `0s` — **the harness produces a
  doubled window here, with the fix applied**, and the test's chosen origin
  hides it. (That is the `pl.Wakeup` gap; see **I2**.)
- The `INCONCLUSIVE: the job never finished` guard (`:147`) checks only
  `unarmedAt.IsZero()`, which the flow sets unconditionally once its deadline
  passes. It **cannot** fire for the failure it is named after.

**Concrete failure scenario:** measured — the entire `./gui/` suite is green with
the post-block `syncArmed` deleted (38.3 s, §2(a)). The one test written to pin
it does not exercise its subject, so any future regression in row-2 handling of
engrave-side edges lands silently.

**The design's Gate-coverage mutation table is wrong in the cells that matter.**
Measured against the real tree:

| mutant | design says (test 1 / test 2) | measured (test 1 / test 2) |
| --- | --- | --- |
| delete **pre-block** | KILLED / KILLED | KILLED, `5m59.99s` (assertion) ✓ / **fails via the INCONCLUSIVE guard, not the assertion** |
| delete **post-block** | SURVIVED / SURVIVED | SURVIVED ✓ / SURVIVED ✓ — but against a test that never runs a job |

So three of the four cells do not mean what the table says, and the R0 primary
question was posed on top of them.

**Smallest fix.** In test 2: set `p.engraver = newEngraver()` before building the
job; assert `splineEntered` (or `job.status.State == engraveDone` and
`Error == ""`) *before* the timing assertion, so a job that never ran is an
INCONCLUSIVE rather than a PASS; and rename `unarmedAt` → `cutEndAt` (it records
the moment the guard **arms**, i.e. the cut's end, not a disarm). With those
three changes the test becomes the honest version of the experiment in §2(b).
Then re-run the mutation table and replace it in the design.

### I1 — IMPORTANT: the code and the design both assert a protection the post-block call does not provide

`/scratch/code/shibboleth/seedhammer-f106/gui/run_flow.go:55-64` and `:195-198`;
`DESIGN_f106_late_arm_edge.md:131-136`.

> `// after   catches an edge created by the ENGRAVE GOROUTINE finishing a cut`
> `//         while the loop slept, which is row 2's actual subject and which`
> `//         only this call can see.`

`only this call can see it` is false — §2 shows the next pre-block call sees it
one turnaround later, with no blocking call in between. `Neither call subsumes
the other` is false in the direction that matters: the pre-block call subsumes
the post-block call up to one turnaround.

**Concrete failure scenario.** This is the "comments outlive their conditions"
class the project already gates on. A future maintainer reading
`run_flow.go:195-198` will believe row 2's cut-end guarantee depends on that
line; the whole suite says otherwise, and the design says otherwise once C1 is
fixed. Equally, someone deleting the line on the strength of a green suite will
believe they removed dead code, when they in fact moved the async-edge branch
decision one tick late — and `armed := ctx.wipe.armed()` is the "obvious"
replacement that is actually unsafe (§2, Recommendation).

**Smallest fix.** Replace both comment blocks with what is measured:

- the pre-block call catches a **flow-created** edge on the frame it happens,
  which is F-106 and is worth a wakeup;
- the post-block call catches an **engrave-goroutine** edge at the end of the
  block rather than at the start of the next iteration — **one turnaround, not
  one wakeup** — which keeps that tick's branch selection consistent and saves
  one extra wakeup; and state plainly that no test pins it and that deleting it
  costs at most one screensaver frame.

Add the same correction to the design's §"The fix", and add the point the design
is missing and that is its strongest argument: **the two-call structure does not
change the set of stamps, only their timing, and only ever earlier** — so it can
make the window fire sooner but structurally cannot extend one.

### I2 — IMPORTANT: the fix's coverage of engrave-side edges rests entirely on `pl.Wakeup()`, which the design never states and the harness does not model

The pre-block call cannot see an edge created while the loop is inside
`AppendEvents`. For those edges the window is only as prompt as the wakeup. That
is fine on hardware because `engraveJob.Start()`'s goroutine does
`defer e.pl.Wakeup()` (`gui/engraver.go:110`) and
`cmd/controller/platform_sh2.go:378-393` returns early on `<-p.wakeups`
(`:420-428`) — I verified both. The design states neither.

**Concrete failure scenario — the `engraveStopping` park.** `EngraveScreen`
installs its 500 ms poll only when `Status().State == engraveRunning`
(`gui/gui.go:2766-2769`). `Stop()` sets `engraveStopping`
(`gui/engraver.go:88`), for which `armed()` is still false
(`gui/wipe_guard.go:53-58`) and the poll is **not** set — so the loop parks to
`idleWakeup`, up to three minutes. When the goroutine finishes, only
`pl.Wakeup()` un-parks it. If that wakeup were ever dropped, the arm edge would
be processed at the idle deadline and row 2 would restart the window there —
**F-106's exact shape, recurring for cut ends**, and no host test would see it:
measured, that is precisely what `deadlinePlatform` does today (C1's trace,
warning at `6m0s` against a `3m0s` spec, with the fix applied).

This is not hypothetical geometry: `Stop()` is the Back-mid-cut abort that
`gui/unlock_session.go:199-203` calls §10.2.2's "most ordinary recovery".

**Smallest fix.** (a) Name the dependency in the design and beside the
post-block call: *engrave-side edges are covered by `pl.Wakeup()`, not by either
`syncArmed` call*. (b) Add the **Back-mid-cut abort** (`engraveStopping` →
terminal) to the hardware re-verification already scheduled alongside the
F-107/F-108 abort→resume seam — untouched screen, Back at ~1:00 into a cut,
warning must appear 3:00 after the head stops. (c) Optionally have
`deadlinePlatform.AppendEvents` select on `testPlatform.wakeups` so the harness
stops silently diverging from the device on exactly this path (I prototyped it
as `wakePlatform`; it is 12 lines and changes no existing result).

## 4. Explicitly checked, no finding

1. **Can the pre-block call make the window NEVER fire? No.** Measured: a flow
   that reinstalls an armed `&wipeGuard{}` on **every frame** produces no arm
   transition, the `armed != a.armed` guard holds, and the warning lands at
   exactly `3m0s`. A per-frame nil↔guard *toggle* cannot sustain itself — the
   unarmed frame parks the flow in the screensaver, which is documented
   pre-existing behaviour — and does not exist in production: `ctx.wipe` has
   exactly three assignment sites (`gui/unlock_session.go:89,90` and
   `gui/unlock_kdf.go:136,137`), all bracket-scoped with `defer`-restore spanning
   many frames. Decisive point: the fix does not change the *set* of stamps, only
   their timing, and only ever **earlier** — a stamp moved earlier makes the
   window start earlier, so the wipe fires sooner or at the same time, never
   later.
2. **`unlockPassphraseFlow`'s bracket handover.** Measured end to end: row-4
   guard installed → held while typing → restored to `prev` (nil) for the row-5
   KDF gap under `KeepAwake` → row-1 guard installed. The warning lands
   **`3m0s`** after the row-1 install (same test with the pre-block call deleted:
   `6m0s`, so it is a real assertion). The handover produces disarm (no stamp) →
   arm (stamp), which is the correct row-1 window origin. The clock is **not**
   restarted when the passphrase bracket closes, because `syncArmed` stamps only
   on the *arming* direction.
3. **Is `a.armed = false` at session start still correct? Yes.** The session loop
   builds a fresh `ctx := NewContext(pl)` (`run_flow.go:47`) whose `wipe` field
   is nil, so `armed()` reads false at the new first pre-block call and matches
   `a.armed = false` — no phantom transition, no stamp. Post-wipe re-entry is the
   same: the deferred `ctx.wipe = prev` restores onto the **abandoned** Context.
   `TestRunSealedPayloadReentryAfterWipe` covers this and is green.
4. **The extra wakeup: exactly one, and it cannot compound.** Measured trace of
   the F-106 scenario — the pre-block call stamps `start=10ms` while `ctx.Wakeup`
   still holds `3m0s` (computed from `start=0s`); the loop sleeps to that stale
   deadline, wakes at `3m0s`, finds `idle == false`, reschedules to `3m0.01s`,
   and the warning lands at `3m0.01s`. No second extra wakeup, because
   `syncArmed` is a no-op without a transition — so the count of extra wakeups is
   bounded by the number of arm transitions, which is bounded by brackets and cut
   ends, not by frames.
5. **Can arming change between the post-block call and the `idleWakeup`
   computation? No.** Only `ctx.Reset()`, `ctx.Router.Events`, and the
   `wipeNowHook` check run in between; none of them runs flow code.
   `armed()` changes only via a flow assignment to `ctx.wipe`/`g.job` or via
   `Status()` draining `e.errs` — and `Status()` on that path is reached only
   from `armed()` itself.
6. **Test 1 asserts what its name says.** Traced: the pre-block call stamps at
   `10ms` (guard install), the warning draws at `3m0.01s`; with the pre-block
   call deleted the same assertion reports `5m59.99s`, matching the hardware
   reading to the tick. Both inconclusive guards (`armedAt.IsZero()`,
   `warnAt.IsZero()`) can fire. A 5 s tolerance against a factor-of-two defect
   cannot mask it. **Test 2's 5 s tolerance is not the problem** — the
   measurement basis is (C1).
7. **`row 2` firing on guard installation is correct against §10.2.4** (spec
   §10.2.4, `SPEC_encrypted_payload_delivery.md:1302-1352`): "resident" is a
   lifetime, the guard is the seam, so the window must open at installation.
   Only the attribution is wrong (M1). The design's rejection of alternative 3
   ("make row 2 not fire on installation") is right and should stay.
8. **Hygiene, re-run.** `gofmt -l gui/run_flow.go gui/idle_late_arm_edge_test.go`
   → clean. `go list -f '{{.IgnoredGoFiles}}' ./gui/` → `[debug.go]` only, so no
   test file is currently hidden by an implicit GOOS/GOARCH constraint (the
   `_arm` hazard the design found is closed, and the check is worth keeping).
   Baseline `go test ./gui/...` green (`38.340s`). Diff is
   `gui/run_flow.go | 60 insertions(+), 21 deletions(-)` plus a 162-line new
   test file.
