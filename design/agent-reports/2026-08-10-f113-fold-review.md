## 1. THE RISK I MOST WANTED CHECKED — is the new `check_public` guard broader than what it front-runs?

**`crates/me-cli/src/seal/mod.rs:121-123`** (in the fold):

```rust
if matches!(classify(r), Ok(Format::Ms)) {
    return Err(SealError::SecretInPublic(i));
}
```

placed ahead of `record::validate_record(r).map_err(SealError::Record)?.is_secret()`.

**Does it narrow the accept set (reject something previously admitted)? No — verified by code
trace.** `classify(s) == Ok(Format::Ms)` is recomputed *identically* inside `validate_record`
(`crates/me-cli/src/seal/record.rs:114`, same trim-then-classify function on the same string),
and the `Format::Ms` arm of `validate_record`'s match (`record.rs:130-159`) can only ever
produce `Err(MsTooLong)`, `Err(Invalid)`, or `Ok(RecordKind::Ms)` — never a non-secret
`RecordKind`. So for any input where `classify` says `Ms`, the pre-fold path could *never*
have admitted it to the public section either — it always errored or was `is_secret() == true`.
No accept-set narrowing.

**But it IS broader in a different, real way: it fires on the bare 2-character HRP text,
skipping `validate_record`'s canonical-form, case, and actual-parse checks entirely — for ANY
string, valid or not.** Verified on the real binary, before (`ccc884a`) vs after (`cca070c`),
on three constructed candidates, none of which are genuine over-length secrets (the case M1
targeted):

| candidate | before (`ccc884a`) | after (`cca070c`, this fold) |
| --- | --- | --- |
| `"ms1" + "q"×50` (53 chars, fails codex32 checksum — not a real secret) | `invalid record: string length 53 outside v0.1 set [50, 56, 62, 69, 75]` | `record 0 is secret material and cannot ride in the public section — it would be engraved and readable in the clear (§6.3)` |
| `"ms10entrs qqq...utd7mdh2lc8h2"` (space-interrupted, 90 chars) | `non-canonical record: separator ' ' at byte 9 — records must be unbroken. If this came from \`mnemonic bundle\`, re-run with --group-size 0: …` | same "secret material" message |
| `"MS10ENTRSQQQ...UTD7MDH2LC8H2"` (uppercase, otherwise-valid 90-char ms1) | `record has an uppercase character at byte 0 — records must be lowercase, or the same wallet has two different public-data hashes (§6.4)` | same "secret material" message |

Commands run: `me seal --plaintext "<candidate>" --out …` at both SHAs (built with
`cargo build --release --bin me` at each).

**The commit message's own justification — "Go orders these deliberately; this matches it" —
is false for two of the three candidates, verified against the real Go logic
(`seal/record.go`).** Go's `Classify` (`seal/record.go:194-223`) only reaches
`ClassCodex32Secret` if `codex32.New(s)` *actually parses and validates* the string — a real
check, not an HRP-text match. Ran the same three candidates through `seal.AdmitSection` in a
throwaway scratch test (`seal/zzscratch_test.go`, written, run, then deleted — worktree left
clean):

```
junk (53 chars):      seal: record classification not permitted in this section: record 0
                       classifies as unknown format, which the public section does not permit
nonCanon (90 chars):  seal: record classification not permitted in this section: record 0
                       classifies as unknown format, which the public section does not permit
upper (90 chars):     seal: record is not lowercase: record 0, byte 0
```

Go never says "secret" for any of these three — the junk and non-canonical cases classify as
`unknown format` (Go's `Classify` requires a real `codex32.New` success to call something a
secret at all), and the uppercase case is caught by Go's unconditional lowercase pass
(`seal/record.go:255-256`), which runs *before* classification, for every record regardless of
HRP. Rust's new guard bypasses the Rust analogue of that ordering for anything with an
`ms`-shaped HRP prefix.

**Impact: message-quality only, not a leak or a wrong admit/refuse decision.** All three
candidates are refused both before and after (`exit=4`, no output file, both then and now) —
same "both refuse, only the reason differs" shape that M1 itself was. The new failure mode is
that a garbage or malformed record that was never validated as an actual secret is now
unconditionally *called* "secret material," which is a stronger, false claim rather than a
suppressed true one.

**Smallest fix — already written, in the ORIGINAL whole-diff review, and not what got
implemented.** The prior report's own M1 remedy:

```rust
match record::validate_record(r) {
    Ok(k) if k.is_secret() => return Err(SealError::SecretInPublic(i)),
    Err(record::RecordError::MsTooLong(_)) => return Err(SealError::SecretInPublic(i)),
    Err(e) => return Err(SealError::Record(e)),
    Ok(_) => {}
}
```

Hand-traced against all three candidates above: `Invalid`, `NonCanonical`, and `NotLowercase`
all fall into `Err(e) => return Err(SealError::Record(e))`, so all three candidates get
**exactly the pre-fold message, unchanged** — and the real M1 target (`Err(MsTooLong(_))`)
still becomes `SecretInPublic` as required. This fixes M1 with none of the three regressions
above.

**Severity: Minor.** Same class as M1 itself (diagnosis-quality, both refuse, no leak, no
SPEC-level admit/refuse change — checked `design/SPEC_encrypted_payload_delivery.md`, which is
normative about what gets admitted/refused, not about exact message wording). Not blocking, but
concrete, verified, and the fix is a known quantity.
