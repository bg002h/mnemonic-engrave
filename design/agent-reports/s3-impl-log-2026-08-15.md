## 2. THE FINDING THE RED OUTPUT CONTAINS, and the judgement call it forced

**The plan's gate for S3 was not satisfiable by the change the plan describes,
and running it is the only way that surfaced.**

`TestRestoreDocNamesNestedSegwit` was written against the *production* path
(assemble a real md1, expand it, call `multisigRestoreLines`) rather than against
`desc4Display` on a hand-built `Template`. Its red output is not "the name is
wrong" — it is **"the restore doc names no script type at all."**

Measured, not inferred:

- SPEC §2.2 D-3 and §4.4 name `gui/multisig_restore.go:51` as the call site that
  matters most. That site is `desc4Display`, and it sits on the **display-only**
  branch of `multisigRestoreLines`, reached only when `expandedToDescriptor`
  returns `expandTemplateOnly` / `expandUnsupported`.
- Every md1 the Build flow authors is `sortedmulti` over full xpubs, i.e.
  **bip380-expressible**, so `expandStatus == expandOK` for all three templates.
  Measured on assembled md1s: `wsh`, `sh(wsh)` and bare `sh` all returned
  `expandStatus=0`.
- On that branch the lines were `Descriptor:` + the chunked descriptor + the two
  addresses. `desc4Display` is never called, so `scriptName` never runs.
- `supplyMultisigPolicyFlow` cannot reach it either: it gates on
  `allSlotsHaveXpub`, so a template-only supplied md1 is refused before the
  restore doc.

So after a correct `scriptName` fix, an `sh(wsh)` walk would have reached the
restore doc and found **nothing** naming the script type, and the plan's gate
would have read as a failed screen.

**JUDGEMENT CALL — flagged for the reviewer to rule on.** I added the type line
to the `expandOK` branch as well:

```
Type:

ltisig (sorted)

...
```

Reasoning: §4.4 says "the restore document is the one that matters most", and
that sentence is false unless the name appears on the branch operators actually
reach. This is the smallest change that makes §4.4 true and the gate satisfiable.
It is additive — the descriptor and both addresses are unchanged, and the test
asserts they are still present.

**The counter-argument, stated so it can be weighed:** on the `expandOK` branch
the descriptor string *already* distinguishes the two — it reads `sh(wsh(` versus
`sh(` — so D-3's "indistinguishable in the restore document" was strictly true
only of the display-only branch. If the reviewer judges the type line to be scope
the plan did not authorise, the correct alternative is to amend the plan's gate
rather than to drop the line, because the gate as written has no other subject on
that branch.

**F-172's premise was also wrong, in a way nobody had caught.** F-172 says the
gate is satisfiable "only if that stage's walk picks Full policy md1". That is
necessary but was not sufficient: on the full-policy arm the restore doc named no
script type either. F-172 identified the right branch for the wrong reason.

### How the walk differs from `walk_build_policy.js`, deliberately

**No hand-derived plate count in `ok` (S0b review I-1).** The existing walks
compute `census.strings.length === plates`, where `plates` is a number written by
hand in a doc comment and is the only driver-supplied term in the verdict. Here
the engrave tail terminates on an **observed** screen (the verify offer), and the
plate count is returned as data. Every term of `ok` is emulator-produced.

**F-172 resolved in the script (S3 owns it).** The `"Full policy md1"` row is
tapped explicitly with a comment saying why: the template-only branch is guarded
by `if !template` and skips the restore doc entirely, so a walk down it would end
with the gate's subject never drawn — indistinguishable from a screen that failed
to say it.

### The blind spot I did NOT paper over — F-179

`shScreen()` is the same `ExtractText` walk over the op tree that `uiContains`
uses, so **a text assertion in the browser walk proves a string was submitted for
drawing, not that it was drawn.** There is no ink hook in the JS API
(`shScreen`, `shScreenSeq`, `shTap`, `shPress`, `shRelease`, `shPace`, `shSysw`,
`shNFC`, `shToolpath` — no raster).

Counter-measure, since a raster floor is not reachable from the browser: I added
`TestRestoreDocNestedNameIsActuallyDrawn`, a Go test that rasterises the real
`multisigRestoreDocFlow` over an assembled `sh(wsh)` md1. Floor is
`buildWalkRasterFloor` (**6000**), not `assertFrameHasBody`'s 4000 — the restore
doc draws **three** nav buttons, and S2's calibration measured a title-only frame
with three at **5482 px**, so the weaker floor would pass a fully blank body on
this exact screen. **Measured: 10,762 ink px.** Every string on the changed
screen is pure ASCII, so the blanking class cannot apply to it.
