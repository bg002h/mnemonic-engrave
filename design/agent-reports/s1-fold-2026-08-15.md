## I3 — "payload record order" was completion order  ✅ behaviour fixed, not the claim

The review was right and the instruction was explicit: make the behaviour match
the promise, or STOP. **The behaviour now matches the promise.** No STOP.

`bundleGatherer.cards` is completion order, and a chunked card completes on its
LAST chunk, so an interleaved payload diverges. Rather than weaken the
announcement, the fold buys the guarantee upstream:

`groupRecordsByCard` (`gui/multisig_build_payload.go`) makes each card's chunks
**contiguous, in first-appearance order**, at the single seam both consumers
read — `buildCosignerSource`. From there the pre-check's assembly and the
gather's own feed get the same list, so completion order and record order cannot
disagree. Grouping is a permutation only: it never drops, invents, or reorders
within a card.

Reproduced first, and kept as a guard rather than a claim
(`TestInterleavedPayloadStillAssemblesInRecordOrder`):

- records `A1 B1 B2 A2` fed raw → `supply[0]` is card **B** (`fp b8688df1`),
  card A second. The test **Fatals INCONCLUSIVE** if that ever stops happening,
  so the fix cannot pass because the defect quietly disappeared.
- the same records grouped → card **A** leads, as the payload lists them.
- plus: grouping is a permutation (multiset equality), leaves an
  already-contiguous payload byte-identical, and keeps a standalone md1 in place.

The three sites the review named:

| site | before | after |
| --- | --- | --- |
| `gui/multisig_build_payload.go` announcement | "in payload order" printed unconditionally, and false for an interleaved payload | **now true**, because the behaviour changed |
| `gui/sysw_session.go` "nothing downstream may reorder them" | absolute | states what `takeAll` *can* promise, and names `groupRecordsByCard` as where the card-order guarantee is actually obtained |
| `gui/bundle_flow.go` "Fed in PAYLOAD RECORD ORDER and never reordered" | absolute | says the loop reorders nothing, that this alone does **not** give record order downstream, and which side of the seam owns the guarantee |

The review's own point about why this mattered is now recorded in the code: with
fingerprints omitted by default a wrong order is invisible in every artifact —
§0.1 clause 2's refuse side — so announcing it as true was the defect, not the
wording.

**Mutation M20** — `groupRecordsByCard` becomes the identity →
`--- FAIL: TestInterleavedPayloadStillAssemblesInRecordOrder`, suite exit 1.

## I1 — the flow's wiring is now asserted  ✅ all four survivors die

`TestBuildOverSupplySelectionIsWalkable` was the only test that ran the real
flow, and it asserted only that it reached "Seed". It now drives the flow to the
**Policy Review** and reads it.

What changed in the test, and why each piece is load-bearing:

- **`USE(1) / SKIP(2) / USE(3)`** — the chosen set is **non-contiguous**, so
  "the operator's selection" and "the first `open` cards" are different answers.
  This is the deselect/reselect shape the brief asked for.
- **self slot `@1`, not `@0`** — with the self key at @0,
  `buildCosignerOrigins(p.N, 0, chosen)` is indistinguishable from the real call
  and M16 is a no-op.
- **fingerprints INCLUDED** — with them omitted every slot renders `(no fp)` and
  a policy built from the wrong cards looks exactly like one built from the
  right ones. This is what makes M15 (duplicate keys) observable at all.
- **`readReviewPages`** — the Policy Review is eight lines once the announcement
  is on it; an assertion that only read page 1 would stop seeing the per-slot
  fingerprints.
- **a FOURTH master for the self seed.** `testSeedPhrase` is masterB, which *is*
  fixture 1 — the card this walk skips — so "the skipped card's fingerprint is
  absent" was unsatisfiable. Caught by the assertion failing on correct code,
  which is the useful direction. The uniqueness guard is scoped to the four keys
  the test names, because fixtures 0 and 3 share masterA's fingerprint **by
  design** — the delivered payload has exactly that collision (`A@0`, `A@1`), so
  demanding four unique fingerprints would demand a payload the machine will not
  meet.

Asserted on the review, verbatim from a passing run:

    PolicyReview Slots@0and@2filledfromthepayload(cards1and3of4,inpayloadorder).
    Policystub:64470659 Slots: @0fp73c5da0a @1fpb8688df1 @2fp28645006
    FingerprintsINCLUDEDoneveryslot.

`@0` = fixture 0, `@1` = the self key, `@2` = fixture 2 — the cards the operator
actually chose, in the slots they actually landed in.
