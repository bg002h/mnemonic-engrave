## Findings

**F1 — Important — the BIP draft (`bip/bip-mnemonic-key.mediawiki`) contradicts itself on the exact rule F-128 just fixed, and was not touched by F-128.**
`bip/bip-mnemonic-key.mediawiki:37-38,428` vs. `:577-586`.
Confirmed untouched in this cycle: `git log --oneline 0feaaaa..main -- bip/bip-mnemonic-key.mediawiki` returns nothing; last touch was `3462157` (2026-08-15), before F-128 (2026-08-21). The BIP's own design goal states "Make an independent implementer following only `bip/bip-mnemonic-key.mediawiki` reconstruct mk1 cards byte-identically to the shipped `mk-codec`" (`design/SPEC_mk1_bip_alignment.md:9`). As it stands, an implementer who reads only the Terminology glossary (line 37-38) or the "Policy ID stubs" payload-field section (line 428 — the BIP's structural analogue of SPEC §3.3) would build an **unconditional-WalletPolicyId** implementation, silently wrong for every keyless-template card — while the same document's "Linkage to MD" section (577-586), a few hundred lines later, correctly states the form-aware rule. This is the identical defect class F-128 just fixed in `SPEC_mk_v0_1.md`, left standing in the sibling artifact meant for actual BIP submission. History: `design/FOLLOWUPS.md:26` records that the BIP WAS rewritten in lockstep for the *first* supersession (2026-06-10, unconditional WalletPolicyId) but there is no record of a second lockstep edit for the form-aware correction (2026-06-19 code change / 2026-08-21 spec text) landing in the BIP glossary or "Policy ID stubs" section — only in "Linkage to MD", apparently from a separate, later BIP-alignment cycle (`design/SPEC_mk1_bip_alignment.md` item C-I5, whose own text claims lines "37/48/268/404" were *already* form-aware at authoring — that claim does not hold against the current file, so either it was inaccurate when written or those specific lines regressed since; not resolved further, out of this review's primary scope).
Not funds-lossy on its own — SPEC §5's own step 4 (Wallet Instance ID recompute) is the actual cryptographic backstop, and this defect, like the one F-128 fixed, would only manifest as spurious "wrong card" rejections for template-form cards, per SPEC's own funds-relevant framing. Rated Important, not Critical, on that basis — but it is the exact class of error F-128 exists to eliminate, in the document the constellation is furthest along toward publishing externally.
*Suggested wording:* rewrite lines 37-38 and 428 to the same form-aware dispatch as lines 577-586 (mirror `SPEC_mk_v0_1.md` §3.3's table), and add a note at 428 pointing to "Linkage to MD" so the two sections cannot silently diverge again.

**F2 — Important — `docs/MK_CODEC_RUST_API.md` describes a formula that never existed and cites a function that does not exist in `md-codec`.**
`docs/MK_CODEC_RUST_API.md:90-103`.
"Cross-binding with md-codec" states the stub is "the first 4 bytes of `SHA-256(canonical wallet-policy preimage)`" and shows example code calling `md_codec::compute_policy_id_stub(&md_template, &xpubs)`, closing with "The md-codec crate exposes `compute_policy_id_stub`." Verified against `crates/md-codec/src/identity.rs` (full-repo grep, `descriptor-mnemonic`): **no such function exists**. Only `compute_wallet_policy_id` (`identity.rs:186`) and `compute_wallet_descriptor_template_id` (`identity.rs:71`) exist, matching the (correct) names used everywhere else in this cycle's diff. Pre-existing (last touched 2026-08-14, before this cycle's range, so not caused by F-128), but it is a live doc-comment describing the exact concept this review is chartered to check, and it is wrong under every formula this project has ever shipped — not just the pre-F-128 one. An implementer following this guide's example would get a compile error.
*Suggested wording:* replace the example with the real form-aware dispatch (`is_wallet_policy()` → `compute_wallet_policy_id` / `compute_wallet_descriptor_template_id`), matching `crates/mk-cli/src/cmd/mod.rs:102-125`'s doc comment.
