## 1. What changed

- **Patch.** It moved from `design/patches/` to `nix/patches/picotool-2.3.1-seal-clear-fix.patch`.
  The header names upstream `3c743bd`, both hunks, the investigation report, and how to drop the
  patch. `patch -p1` ignores the header. The `design/patches/` copy is deleted.
- **`flake.nix`.** `picotoolFor pkgs` asserts `pkgs.picotool.version == "2.3.1"` and then applies
  `overrideAttrs` with the patch appended to `patches`.
  - It is used by `packages.picotool`, `default` and `devShells.otp`.
  - `packages.picotool-unpatched = pkgs.picotool` exists for the negative control and is not used by
    any shell.
  - **One deviation in form, not in effect:** the patch goes in through
    `builtins.path { path = ./nix/patches/…; name = …; }` rather than a bare `./nix/patches/…`.
    - A bare path evaluates to a subpath of the flake's `-source` store path. Under Nix 2.34 the drv
      still copied the file on its own, but on other Nix versions the patched store path could
      depend on the whole repo.
    - With `builtins.path`, the store path depends only on the patch bytes and nixpkgs.
    - Both forms gave the same out path here: `ri9krl08…`.
- **`scripts/lib/seal-check.sh`** (new). `seal_has_clear_entry "$INFO"` matches
  `^[[:space:]]*load map entry 0:[[:space:]]+Clear 0x20000000->0x20082000$` with a here-string. Both
  `sign-firmware.sh` and the test use it.
- **`sign-firmware.sh` step 7.** It sources the lib. After `signature: verified` it now runs
  `seal_has_clear_entry "$INFO" || die "…"`.
- **`scripts/test/seal-clear-test.sh <picotool> [--expect-fail]`.** It does what plan §2 asks:
  - the fixture's sha256 is checked first;
  - `seal --sign --clear` must exit 0;
  - every `signature:` line must be `verified`, never another verdict;
  - the exact Clear line must be present;
  - a tamper control XORs 0x01 into byte 32, after asserting that block 0 targets `0x10000000`,
    and requires `incorrect`;
  - a seal without `--clear` must verify and carry no Clear entry;
  - the shared check must accept the `--clear` output and refuse the no-`--clear` output;
  - a wiring check confirms that `sign-firmware.sh` sources the lib and that
    `seal_has_clear_entry "$INFO"` is followed by `|| die`.

  `--expect-fail` requires 248 and "unknown sram end", skips the tamper control, and still runs
  steps 4 and 5. Comments cite 2.3.1 `main.cpp:3824`/`:3809-3810` (load map print) and `:3868`
  (signature print).
- **Fixture** `scripts/test/fixtures/seal/blinky.uf2` (sha256 `e48659d7…54a9`, 47,104 bytes). Its
  provenance is fully established:
  - I rebuilt it **byte-for-byte**, using R's exact `build_blinky` command

## 5. Findings, deviations and ambiguities

1. **A plan fact proved false: P7, "nix sandboxed builds fail in this container".**
   - `nix build` of `.#picotool` succeeded here (`sandbox = true`, nix 2.34.6), as did
     `nix develop .#otp`.
   - So the patched binary was built by nix locally, not only in CI. All local seal-test and probe
     runs above used it.
   - The native builds were used only for the mutants.
   - CI remains the gate of record. The CI run itself has not happened, because nothing is pushed.
2. **A new picotool bug, independent of the patch: `der_to_raw`** (`bintool/mbedtls_wrapper.c:169`
   and `:179` at 2.3.1, also in 2.2.0-a4).
   - The code is `memcpy(r + (32-b2), der + 4, (32-b2))`; the length should be `b2`.
   - Whenever r or s is below 2^247, picotool's own `seal --sign` signature is wrong.
   - Measured: 7 of 500 test runs red on patched 2.3.1 and 3 of 200 on 2.2.0-a4 before the fix,
     and 3 bad signatures in 1500 seals, each `00XX` followed by 60 zeros in one half.
   - This made the plan's test **flaky (~1%)** as written. I stopped and fixed it in its own commit
     (`0de77eb`), not by weakening the check:
     - a seal is retried with a fresh key, at most twice, **only** when the verdict is `incorrect`
       AND a signature half matches that exact fingerprint (k = 1..4);
     - every other outcome is final on the first attempt;
     - the hunk-B mutant is still red 50/50.
   - **This is a change to the plan's test design that no reviewer has seen.** The post-implementation
     review should judge it. If it is rejected, revert `0de77eb` and accept the flake, or patch
     `der_to_raw` too (a third hunk, outside this GREEN plan).
   - Our signing pipeline does not depend on picotool's signature:
     - `sign-firmware.sh` and the fork take the final signature from `picosign`, which left-pads;
     - R's `make_otp_json` discards the sealed image.

   Added to the upstream issue draft as a separate bug.
3. **Hold wording.** It is verbatim. The RUNBOOK adds one sentence after it: `sign-firmware.sh`
   refuses an image whose load map lacks the Clear entry (SP2-M1's suggested backstop).
4. **The E3a plan R0 line.** Beyond naming the Clear entry, it also asks Brian to run the seal test
   and check the patched store path, which is SP-M5's suggestion. The wording is mine.
5. **CI shellcheck list.** Only `seal-clear-test.sh` was added, as the plan says; `-x` follows it into
   `seal-check.sh`. `sign-firmware.sh` passes shellcheck but is not on the CI list (unchanged
   scope).
6. **x86_64-darwin evaluation** prints a nixpkgs release-note warning; aarch64-linux and
   aarch64-darwin evaluate to `picotool-2.3.1`. None of these were built.
7. **Upstream issue draft** (`design/agent-reports/picotool-upstream-issue-draft.md`). Line numbers
