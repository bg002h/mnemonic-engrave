## 1. The harness change (`deadlinePlatform.AppendEvents`)

Traced the whole mechanism independently rather than trusting the comment:

- **`p.wakeups` coalescing is sound.** `testPlatform.Wakeup()`
  (`gui/gui_test.go:407-413`) does a non-blocking drain then a send on a
  buffered-1 channel — at most one item ever sits in the channel. The new
  `select { case <-t.C: case <-p.wakeups: }` in `AppendEvents`
  (`gui/run_harness_test.go:87-92`) consumes it once; the next call finds the
  channel empty and takes the timer/floor. The comment's literal claim ("a
  pending wakeup is consumed once and the next block takes the floor again")
  is true as stated.
- **`defer t.Stop()` is fine.** go1.26.3 timers don't need channel-drain
  discipline to avoid leaks (that requirement predates Go 1.23), and `t` is a
  fresh, unshared `time.NewTimer` per call — no reuse, no synctest-specific
  hazard.
- **Does a stray `Wakeup()` from elsewhere shorten a block a test depends on
  being long?** Grepped every `.Wakeup()` call site in non-test code:
  `gui/gui.go:321` (`ConfirmDelay.Progress`, fires every frame during a
  press-and-hold confirm), `gui/engraver.go:110` (the intended one,
  job-goroutine exit), `gui/qa.go:48` (the QA self-test screen, unrelated).
  `ConfirmDelay.Progress` calling `Wakeup()` on every frame during a hold is a
  real mechanism that, if driven through `deadlinePlatform` by some future
  test, would let `AppendEvents` return near-instantly every iteration
  without ever advancing virtual time by the floor — the "cannot livelock"
  framing is narrower than it reads (it defeats a *stale* pending wakeup, not
  a caller that resignals every tick). **But no test today reaches it**: I
  checked all seven files that construct a `deadlinePlatform`
  (`run_reentry_test.go`, `idle_late_arm_edge_test.go`,
  `idle_realclock_diag_test.go`, `run_flow_scrub_test.go`, `run_flow_test.go`,
  `run_harness_test.go`, `unlock_passphrase_wipe_test.go`) — none drives
  `ConfirmWarningScreen`/`EngraveScreen`'s hold-to-confirm UI or
  `qaEngraveFlow`; they all assign `ctx.wipe`/call `job.Start()` directly.
  No concrete failure scenario exists against the current tree → **Nit**, not
  a blocker (see §4).
- **`TestRunPostCutWindowRestartsFromCutEnd`** (the pre-existing row-2 test
  round 0 cited as exercising a genuine mid-park edge) uses `fakeRunningJob()`
  and flips `job.status.State` directly from `p.onDirty`, never touching
  `p.wakeups` — unaffected by the harness change by construction. Confirmed
  green under `-race`.
- Ran the harness-affected tests under `-race`: `TestIdleWindowIsNotDoubledByALateArmEdge`,
  `TestCutEndingDuringTheParkStartsAFreshWindow`,
  `TestCutEndingAfterTheDeadlineStartsAFreshWindow`,
  `TestRunPostCutWindowRestartsFromCutEnd` — all green, no races.

## 2. Do the three tests assert what they claim?

- **INCONCLUSIVE guards actually fire.** I mutated out `p.engraver =
  newEngraver()` in both `TestCutEndingDuringTheParkStartsAFreshWindow` and
  `TestCutEndingAfterTheDeadlineStartsAFreshWindow` (verified the diff applied
  before testing) — both correctly report `INCONCLUSIVE: the spline never ran
  to its end` and FAIL, rather than silently passing the way C1's original bug
  did. This is the exact false-PASS class round 0 killed, and it does not
  recur.
- **`cutEndAt` happens-before is real.** Written on the engrave goroutine,
  published via `close(cutDone)`, read after a non-blocking `select` that only
  proceeds once that case is ready — a valid Go memory-model happens-before
  edge (close-before-receive), not just "probably fine because it's a test."
  `go test -race` agrees on all three tests.
- **`TestCutEndingAfterTheDeadlineStartsAFreshWindow`'s screensaver-active
  premise, retraced independently:** `p.tickFloor = 2s`, `cutDuration =
  idleTimeout + 10s = 3m10s`. `a.idle.start` is untouched between session
  start and the cut ending (job running disarms but does not stamp), so
  `idleWakeup ≈ 3m` from session start — the screensaver activates at `t=3m`,
  well before the cut ends at `t=3m10s`. At that point `armed=false` (job
  running) and `idle=true` routes to the unarmed screensaver branch
  (`run_flow.go:277-307`), whose 40 ms `WakeupAt` request is floored to the
  test's 2 s `tickFloor` — so the loop is genuinely polling every ~2 s when
  the cut ends, matching the test's own comment that `pl.Wakeup()` is *not*
  what un-parks this one (the saver's own poll is). Consistent with
  `TestCutEndingDuringTheParkStartsAFreshWindow`'s `cutDuration =
  idleTimeout/2 = 90s` case, where the loop genuinely is parked in a single
  long `AppendEvents` and only `pl.Wakeup()` un-parks it. Both test comments
  describe the mechanism accurately.
