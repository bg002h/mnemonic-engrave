## C1 — CRITICAL: The runbook's mechanical verification gates cannot be executed on the SeedHammer II — every safety mechanism the rehearsal proves is structurally unavailable at the moment it matters

- **Location:** `design/RUNBOOK_custom_boot_key.md:167-170` ("Better still: use `scripts/pico2-bootkey-rehearsal.sh`'s `make_otp_json`"), `:176-183` ("contains `read_slot()` / `verify_slot_or_die()` … **use that same code here**"), `:94-117` (step-1 slot checks); `scripts/pico2-bootkey-rehearsal.sh:184-200` (`require_board`), `:196-199` (slot-0 tripwire), `:329-578` (phase-only CLI).
- **Finding:** The rehearsal script's only entry points are `--phase 0..6`. Every phase calls `require_board`, which dies unless the connected board's CHIPID matches the pinned rehearsal Pico, and the slot-0 tripwire (`:196-199`) is explicitly designed to **refuse to run against the SH2** ("This script is for the throwaway rehearsal board ONLY"). Phase 0 dies on the SH2 too (`assert_stock_or_die` fails on `SECURE_BOOT_ENABLE=1`). There is no `--verify-slot`, no standalone verify script, no way to invoke `make_otp_json`, `read_slot`, `verify_slot_or_die`, or `check_page_locks` against the real device. The runbook's instructions to "use that same code here" are therefore **impossible to follow**. What remains is exactly what round 0's F3 (Critical) condemned: eyeballing byte-swapped hex — 16 rows for the slot-0 recovery-path check, 48 rows for the slots-1–3-empty check (step 1), the two-way hash agreement (step 2), and, worst, the 16-row readback that is the *sole gate* before the irreversible `KEY_VALID` write.
- **Concrete failure scenario:** Operator completes a green rehearsal, starts the runbook. At step 2, after `picotool otp load`, they try to run `verify_slot_or_die` as instructed → discover the script refuses the SH2 by design → mid-procedure, adjacent to an armed irreversible step, they improvise: paste bash function bodies into an interactive shell (see I1 — their shell is fish, so this fails too), or fall back to reading 16 byte-swapped rows by eye. One transposed nibble later they type the step-3 command and `KEY_VALID 0x2` permanently validates a slot whose contents were never actually verified. If the hash was wrong, a spare slot is consumed; repeat the same manual method on slots 2 and 3 and the device runs out of slots. This is a false transfer of proof: three review rounds hardened the *scripted* verification, and the procedure performed on the real device uses **none of it**.
- **Fix (mandatory before SH2 execution):** Add explicit SH2-mode, read-only entry points to the rehearsal script — e.g. `--sh2-precheck` (step 1: assert slot 0 == `c8314536…`, slots 1–3 empty across all 16 rows each, `KEY_VALID==0x1`, `SECURE_BOOT_ENABLE==1`, page locks clear via `read_row_raw24`) and `--sh2-verify-slot N --key file.pem` (step 2's gating readback), reusing `otp_field`/`read_slot`/`verify_slot_or_die`/`check_page_locks` verbatim, with all write paths structurally unreachable in that mode; plus `--make-otp-json` exposed standalone (it never touches a device). Then **rehearse those exact entry points against the sealed Pico** during phases 2–6, so the tool used on the SH2 is the tool the rehearsal proved. Rewrite runbook steps 1–3 to consist of those invocations and nothing hand-verified.

## I1 — IMPORTANT: Every multi-line command block in the runbook is bash-only syntax; the operator's shell is fish, where they are hard syntax errors — verified empirically

- **Location:** `design/RUNBOOK_custom_boot_key.md:94-95, 100-103` (step-1 `for … do … done` loops), `:161-164` (the step-2 `if … then … fi` abort guard); the runbook itself acknowledges the operator runs fish (`:81`).
- **Finding:** Tested on this machine's fish: `for i in $(seq 0 15); do …; done` → `fish: Missing end to balance this for loop` (exit 127); the `if jq -e … then … fi` guard → `Missing end to balance this if statement`. Pasted as whole blocks, **zero commands execute**; run line-by-line, the loops and the guard are simply unavailable, and `picotool otp load my-otp.json` (`:164`) runs unguarded. The guard's live hazard is admittedly small on an already-sealed SH2 (`crit1`/`boot_flags1` re-writes would be same-value, and slot 0 is protected by picotool's ECC-modification refusal), but the step-1 loops are load-bearing STOP-condition checks, and every failed paste pushes the operator into ad-hoc fish translation — feeding C1's improvisation channel at exactly the gated moments.
- **Fix:** One prominent line at the top of the runbook: "Run every command block in this document inside `bash` launched from the nix devshell" — or better, obsolete the blocks entirely via the C1 entry points. Also note the guard's `exit 1` will close an interactive shell.

## I2 — IMPORTANT: The runbook's irreversible writes have no device-identity binding — the discipline the rehearsal drills on every phase is dropped exactly where it matters most

- **Location:** `design/RUNBOOK_custom_boot_key.md:125-192` (steps 2–3: `picotool otp load`, `otp set -s`, and the step-3 readback), contrast `scripts/pico2-bootkey-rehearsal.sh:184-200`.
- **Finding:** Nothing records the SH2's CHIPID in step 1, nothing re-verifies identity or re-reads slot 0 immediately before the `otp load` or the `KEY_VALID` write (which may happen days after step 1), and nothing tells the operator to disconnect the rehearsal Pico before starting the runbook. picotool refuses to act with two devices connected (round-1 verified; not re-verified here), but a **single wrong device** passes silently.
- **Concrete failure scenario:** The consumed rehearsal Pico (KEY_VALID=0x3) is on the desk next to the SH2. The operator, believing the SH2 is connected, runs step 3's verification `picotool otp get BOOT_FLAGS1.KEY_VALID` — the *Pico* answers `0x3`, exactly the expected value. The operator records the SH2's valid bit as set when the SH2 was never written, flashes the fork firmware, and gets a device that won't boot it, then starts "recovering" a device that has no problem — possibly consuming a slot on a misdiagnosis (see I5). Not directly destructive, but it is a verified-looking false confirmation of an irreversible step.
- **Fix:** The C1 SH2 entry points should pin the SH2's CHIPID at `--sh2-precheck` and require, immediately before *each* write, CHIPID match **and** slot 0 == the SeedHammer hash (the exact inversion of the rehearsal tripwire). Add "unplug every other RP2350" to the preamble.

## I3 — IMPORTANT: Runbook step 1 still reads the page-lock rows with `-e` — a round-1 finding that was fixed in the script but never folded into the runbook, and round 2 marked it FIXED anyway

- **Location:** `design/RUNBOOK_custom_boot_key.md:100-103` (`picotool otp get -n -e "$l"`); the fixed counterpart is `scripts/pico2-bootkey-rehearsal.sh:222-243` (`read_row_raw24`, deliberately without `-e`, full 24 bits). Round 1 explicitly flagged "Same in `design/RUNBOOK_custom_boot_key.md:96-99`" (`…opus-review-round1.md:50`); round 2 verified only the script (`…sonnet-review-round2.md:22`).
- **Finding:** Page-lock rows are `ecc=false`. On a genuinely locked page, an `-e` read decodes ECC-invalid and prints a warning/garbage rather than the non-zero lock value, and bits 23:16 (the third lock copy) are masked away. This is the runbook's **only go/no-go writability gate** on the real device, and on the one input it exists to catch, its output is ambiguous. The failure direction is probably confusion rather than destruction (a locked page would also make the later write fail cleanly), but an ambiguous STOP gate on the irreversible path is not acceptable, and it demonstrates concretely that the GREEN did not cover the runbook.
- **Fix:** Drop `-e`; require the full 24-bit `VALUE` to be zero (or, per C1, replace with `--sh2-precheck` which already contains `read_row_raw24`).

## I4 — IMPORTANT: Rehearsal phase 6 (the fallback control) has no state preconditions and false-PASSes when run out of order

- **Location:** `scripts/pico2-bootkey-rehearsal.sh:556-573`; contrast phase 2 (`:422-424`), phase 4 (`:481-482`), phase 5 (`:514-515`).
- **Finding:** Phases 4 and 5 assert `KEY_VALID` state before drawing conclusions; phase 6 asserts nothing. Run on a board where phase 1 never took (or before phase 1, or after a phase-1 abort mid-1d), the blinky boots because secure boot is off, and phase 6 records "PASS: Both keys boot. Leaving SeedHammer's slot valid really does preserve the fallback" — a **false proof of the recovery path** that runbook step 7 and the entire Recovery section rest on. Phase 3 run out of order fails closed (a blink dies); phase 6 fails open.
- **Fix:** Open phase 6 with `[ $((16#$(otp_field CRIT1.SECURE_BOOT_ENABLE) & 1)) -eq 1 ]` and `KEY_VALID == 0x3` asserts, mirroring phase 5.

## I5 — IMPORTANT: The runbook's failure-diagnosis text invites burning a second slot for a signature-level boot failure

- **Location:** `design/RUNBOOK_custom_boot_key.md:277-287` (Recovery: "Wrong hash burned into a slot → that slot is dead forever. Move to the next free slot"), `:253-258` (step 6 has no failure guidance); contrast `scripts/pico2-bootkey-rehearsal.sh:524-527`, which tells the rehearsal operator to re-sign once (fresh nonce, note M3/high-s) before concluding the chain is broken.
- **Finding:** If step 6's flash doesn't boot, the runbook's only nearby explanation is the "wrong hash" recovery bullet. But if step 2's mechanical readback passed, the burned hash is *proven* correct, and a boot failure is a signing/image problem — retryable at zero OTP cost. The rehearsal's re-sign-first guidance never made it into the runbook. Whether the RP2350 bootrom rejects high-s ECDSA signatures remains unverifiable from this repo (flagged since round 0); if it does, roughly half of all signatures produce exactly this symptom.
- **Concrete failure scenario:** Step 6 fails to boot → operator reads Recovery → concludes the slot is bad → generates a new key, burns slot 2, sets it valid → same boot failure (the actual cause was the signature) → two of three spares gone chasing a re-signable problem.
- **Fix:** Add to step 6: "If it does not boot: the slot readback in step 2 already proved the hash — do NOT burn another slot. Re-run step 5 (fresh signature) and re-flash; official firmware remains bootable throughout." Cheap insurance: make `sign-firmware.sh` loop re-signing until s ≤ n/2.

## I6 — IMPORTANT: `ask_blink` defaults every non-"y" answer to "no", which is the PASSING answer for the negative control (3a/3b) and the real-firmware acceptance check (5b) — and 5b never tells the operator how to check

- **Location:** `scripts/pico2-bootkey-rehearsal.sh:317-323` (`case "$a" in y|Y) yes ;; *) no ;;`), consumed at `:452-458`, `:466-470` (no = PASS), `:542-548` (no = PASS).
- **Finding:** An absent-minded Enter, a typo, or an "idk" at 3a, 3b, or 5b registers as "no" and prints PASS. These are precisely the three checks whose false PASS constitutes a false proof (the script's own header calls phase 3 the point of the whole exercise). Phase 5b compounds it: the question — "Did the board REAPPEAR as a BOOTSEL drive?" — is the only prompt where **y means failure**, inverting the convention the four prior prompts trained, and the script gives no procedure for answering it (on a headless Pico, "accepted but hung" and "operator didn't look" are indistinguishable without running `picotool info` or watching for the RP2350 drive, which the script never suggests).
- **Fix:** Reprompt until the literal answer is `y` or `n`; for 5b, automate the verdict: `sleep 3; picotool info` — a reachable BOOTSEL device means rejected, no device means accepted — and print the command for the operator either way.

## I7 — IMPORTANT: Runbook/rehearsal key files share the basename `my-key.pem` — a throwaway rehearsal key can silently become, or displace, the load-bearing SH2 key

- **Location:** `scripts/pico2-bootkey-rehearsal.sh:353-360` (generates `rehearsal-work/my-key.pem`, explicitly "'yours'"); `design/RUNBOOK_custom_boot_key.md:128` (step 2: `-out my-key.pem`, cwd-relative), `:214` (step 5 signs with `my-key.pem`).
- **Concrete failure scenario:** Days later, at runbook step 5 in the fork directory, `my-key.pem` isn't there; the operator searches, finds `rehearsal-work/my-key.pem`, recognizes the name from "my-key is yours", and uses it. Depending on which steps it leaks into, they either flash an unbootable image (recoverable, confusing) or burn the *throwaway* key's hash into the SH2 — which works, until `rehearsal-work/` is deleted as disposable (the script spends its whole header teaching that rehearsal artifacts are consumed junk), at which point the burned slot can never be signed for again.
- **Fix:** Name the real key distinctively (`sh2-boot-key.pem`), use absolute paths in steps 2/5, and have the C1 `--sh2-verify-slot`/json tooling refuse any key whose hash equals a `rehearsal-work/*.pem` hash.

## Minor findings

- **M1** — `design/RUNBOOK_custom_boot_key.md:149` vs `:194-199`: step 2's `picotool seal` requires `seedhammerii-<version>.uf2`, which is built in step 4 — two steps later. If the 2026-07-26 reproducibility build has been cleaned up, the operator hits "no such file" inside the irreversible step and improvises. Reorder (build before step 2) or add "build now if absent". (Sealing with any real RP2350 image is harmless to the burned value — the json derives from the key alone — so this is confusion, not damage.)
- **M2** — `design/RUNBOOK_custom_boot_key.md:254`: `picotool load --verify "$FW"` — `$FW` is never defined anywhere in the runbook. Fails harmlessly; write the real filename.
- **M3** — `design/RUNBOOK_custom_boot_key.md:271`: the single most catastrophic command in the whole plan (`picotool otp set -s BOOT_FLAGS1.KEY_INVALID 0x1` — permanently revokes the only recovery key) is printed verbatim in copyable form. Defang it (`# NEVER RUN: …` or describe without exact syntax).
- **M4** — `scripts/pico2-bootkey-rehearsal.sh:379-392, 407-410`: a USB drop between 1d's two writes (KEY_VALID set, SECURE_BOOT_ENABLE not) leaves a Pico that no phase accepts — phase 1's resume path requires `KV==0`, `assert_stock_or_die` says "get a FRESH board", phase 2 dies "phase 1 did not take". Recovery needs a manual out-of-script `otp set`. $5 consequence and the write order is the safe one (valid-before-enable can never brick); extend the resume branch if cheap. Note the mirror-image state on the SH2 cannot occur (it arrives already sealed).
- **M5** — `design/FOLLOWUPS.md:11` (`bootkey-rehearsal-fidelity-residue`): the follow-up's own text commits to checking F11(c) — raw redundant-row readback of `0x040-0x047`/`0x04b-0x04d` — "on the SH2 itself during step 1 before the irreversible write", with owning phase hardware-bringup. The runbook's step 1 contains no such commands. Per this project's own burndown rule that item is due *now*, not deferrable past the SH2 write. Mitigation: picotool prints redundant-row warnings visibly on direct reads, so fold the raw reads into `--sh2-precheck` and reconcile the follow-up.
- **M6** — `scripts/pico2-bootkey-rehearsal.sh` (structure): the rehearsal burns slot 1 (phase 4) before ever proving the my-key-signed image is *bootable* — a broken signing chain is discovered only in phase 5, after the irreversible write. A pre-seal positive control (flash the signed blinky before phase 1 seals the board) would separate "image is runnable" from "signature is accepted" and save a board on a chain failure. Improves diagnosis on the Pico only; no SH2 safety impact.

## What the rehearsal structurally cannot prove (and honesty check)

The plan is honest about the big one: factory provisioning of the retail unit (page locks, PICOBOOT restrictions, anything an unpublished jig wrote) is unknowable until the step-1 reads, and writability is unknowable until the first real write (open item 4, corrected in a prior round — accurate as written). Also unverifiable from this repo: bootrom high-s policy (I5), the BOOTSEL-button location claim (`:87-89`), picotool's two-device refusal (asserted round 1, not re-verified here), and silicon-stepping equivalence between a retail Pico 2 and the SH2's RP2350. None of these change the verdict; the first is honestly labeled and the rest are bounded.

## Destruction inventory (the question asked)

- **The Pico 2 is destroyed by design** — 2 of 4 slots plus permanent secure boot. Correctly and repeatedly documented.
- **On the SH2, executing the written commands, the worst reachable outcomes are:** spare slot(s) consumed by a bad burn or misdiagnosis (I5), and the permanent, already-priced loss of the `(UNLOCKED)`-free display. **Bricking is structurally out of reach of the written procedure**: secure boot is already on, slot 0 stays valid (step 7), the recovery signature on official v1.4.3 is verified real, and nothing anywhere writes page locks, `KEY_INVALID`, or BOOTSEL-disable bits — confirmed against `driver/otp/` and the runbook/script text. The catastrophic outcomes all route through **operator improvisation**, and the findings above are precisely the places where the current runbook forces improvisation at gated moments.

## Verdict

**Not safe to execute as written.** The rehearsal script is one small fix set away from ready; the runbook is the weak half, and the prior GREEN never covered it as an operator would run it.

**Minimum changes before the Pico rehearsal:** I4 (phase-6 preconditions), I6 (strict prompts + automated 5b verdict).

**Minimum changes before touching the SH2:** C1 (SH2-safe read-only entry points, rehearsed on the Pico, replacing every eyeball check in steps 1–3), I1 (bash declaration or full scripting), I2 (identity binding before each write), I3 (drop `-e` on the page-lock reads), I5 (step-6 diagnosis text), I7 (key naming), plus M5's follow-up reconciliation. Then re-run this review loop on the folded runbook per the project's own R0 rule.

**Should it be executed at all: yes, after the above.** The risk is fairly priced: the irreversible downside is bounded at spare slots plus a cosmetic suffix, the recovery path is empirically verified, the reject→burn→accept A/B is the right proof structure, and no materially safer route exists — a sacrificial second SH2 would only de-risk the factory-provisioning residue that step 1's reads already gate on. The plan's engineering is fundamentally sound; its remaining defect is that the safety apparatus lives where the SeedHammer isn't.
