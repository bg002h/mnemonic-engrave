FIRMWARE QUICKSTART — build, test, and upload signed firmware
=============================================================
Condensed card. Full detail + rationale: design/RUNBOOK_custom_boot_key.md
Read that before the first real run. This is a reminder, not a substitute.

Every command below runs in BASH, from the fork's nix devshell:

    cd /scratch/code/shibboleth/seedhammer && nix develop

(Your login shell is fish; multi-line bash blocks are syntax errors there.)


00. CONNECTING A BOARD (do the udev step once, before you need it)
--------------------------------------------------------------------------------
Both boards enter BOOTSEL the same way: hold a button WHILE plugging in USB,
release when a USB drive appears.

    Pico 2           BOOTSEL button (the only button on the board)   micro-USB
                     — the official Pico 2 is NOT USB-C
    SeedHammer II    the button on the control board (observed 2026-08-03  USB-C
                     to be labelled "reset"; the manual calls it the
                     firmware button). Hold it while plugging in.

Only the instant of power-up matters -- you do not need to keep holding it.

DON'T GUESS FROM THE LABEL. Verify empirically:

    lsusb | grep 2e8a          # want: 2e8a:000f ... RP2350 Boot
    picotool info              # want: "target chip: RP2350"

2e8a:000f IS the bootrom's BOOTSEL device ID -- normally-booted firmware cannot
present it, and picotool cannot read OTP unless you are in BOOTSEL. If both of
those work, you are in, whatever the button is called.

Both then enumerate as an RP2350 in BOOTSEL, USB vendor ID 2e8a. The SeedHammer's
volume is labelled SHII. USE A DATA CABLE — charge-only cables are the most
common "device not found".

PERMISSIONS — do this once, or picotool will not see the device:

    printf 'SUBSYSTEM=="usb", ATTRS{idVendor}=="2e8a", MODE="0660", TAG+="uaccess"\n' | sudo tee /etc/udev/rules.d/60-picotool.rules
    sudo udevadm control --reload-rules
    sudo udevadm trigger

THE FILENAME NUMBER MATTERS. systemd's /usr/lib/udev/rules.d/73-seat-late.rules
is what turns TAG+="uaccess" into an ACL for your login session, and udev
processes rule files in SORT ORDER. A file named 99-* sets the tag AFTER 73 has
already run, so the ACL is never applied and picotool reports "appears to be in
BOOTSEL mode, but picotool was unable to connect". Anything below 73 works;
60- is conventional. If you already created a 99- file, delete it.

Check it worked -- your user must appear in the ACL:
    ls -l /dev/bus/usb/*/*        # find the 2e8a device's node
    getfacl /dev/bus/usb/001/NNN  # expect a user:<you>:rw- entry

(One line, no heredoc -- safe to paste in BOTH fish and bash. An indented
heredoc silently fails in bash with exit status 0, writing junk filenames into
the current directory and never reloading the rules.)

(uaccess grants the logged-in user access rather than opening the device to
everyone. Unplug and replug the board afterwards.)

DO NOT work around missing permissions by running the rehearsal script under
sudo. It writes keys and state into rehearsal-work/; as root those land
root-owned and the next unprivileged phase breaks partway through — possibly
between two OTP writes. For a one-off check only, use an absolute path, since
sudo does not inherit the nix PATH:

    sudo $(which picotool) info

Verify the connection:

    picotool info                # should report an RP2350

Once that works unprivileged, --phase 0 (Pico) and --sh2-precheck (SeedHammer)
will too. Both are read-only and refuse the wrong board.


0a. RUN THIS FIRST — TODAY. READ-ONLY SURVEY OF YOUR SEEDHAMMER
--------------------------------------------------------------------------------
Do this before the Pico arrives, before building anything, before reading the
rest of this card. It writes NOTHING.

    cd /scratch/code/shibboleth/seedhammer && nix develop
    ../mnemonic-engrave/scripts/pico2-bootkey-rehearsal.sh --sh2-precheck

Put the SeedHammer in BOOTSEL first (section 00). Unplug every other RP2350.

WHY THIS FIRST, AND WHY IT IS SAFE
  The mode contains no otp load, no otp set, no picotool load -- it reads about
  70 OTP rows and stops. Nothing it does is irreversible, and it refuses any
  device that is not a SeedHammer II.

WHAT IT BUYS YOU, TODAY
  1. It retires the biggest unknown in this whole procedure. Whether your retail
     unit has OTP page locks -- or any other unexpected factory provisioning --
     decides whether a second boot key can EVER be added. Non-zero page locks
     mean this procedure is impossible on your device, and reading them is the
     only way to find out short of an irreversible write. Better to learn that
     now than mid-burn.
  2. It is the first time this tooling meets real picotool output. The OTP
     parsers were written from picotool's source and tested against stubs
     written from that same reading -- circular by construction. Real output
     breaks that circle. They fail CLOSED, so a parsing problem shows up as a
     loud error, not a wrong answer.
  3. It confirms the udev rule works on the machine that matters.

IF IT FAILS
  Read the message. It distinguishes "your device is not in the expected state"
  (a fact -- stop, go read the runbook) from a tool problem. Either way you have
  lost nothing: no OTP was touched. Fix and re-run; it is idempotent apart from
  writing the CHIPID pin to sh2-state/.

IF IT PASSES
  Your device is in the expected retail state, its OTP pages are writable, and
  its identity is pinned for later steps. Nothing else here becomes urgent --
  the Pico rehearsal is still mandatory before anything irreversible.


0b. BUILD + PROVE REPRODUCIBLE                                   [safe, anytime]
--------------------------------------------------------------------------------
    env VERSION=$(git rev-parse HEAD) nix run .#build-firmware
    sha256sum seedhammerii-$(git rev-parse HEAD).uf2

Compare against the CI artifact for the same commit (Actions > "Build image").
A match proves your toolchain reproduces CI bit-for-bit. VERSION must be the
raw SHA — CI uses that, and the version string is compiled in.

Known-good: 66d3121... -> 0e576b452f641168a42c28339845a568e5a3ac920d670fb7bef024ccf4c4f9dc

2. REHEARSE ON A PICO 2 — DO THIS BEFORE THE ENGRAVER, ONCE
--------------------------------------------------------------------------------
Plain Pico 2 (not the W — its LED is behind the wireless chip). The board is
CONSUMED: a full run burns 2 of its 4 OTP slots and permanently seals it.

    R=../mnemonic-engrave/scripts/pico2-bootkey-rehearsal.sh
    $R --phase 0                # inventory, pin board, make keys, build payload
    $R --phase 1 --execute      # seal it (mimics a factory SeedHammer)  DESTRUCTIVE
    $R --phase 2                # verify sealed + page locks
    $R --phase 3 --execute      # NEGATIVE CONTROL — images must be REJECTED
    $R --phase 4 --execute      # burn your key                          DESTRUCTIVE
    $R --phase 5 --execute      # same image must now be ACCEPTED (+5b real firmware)
    $R --phase 6 --execute      # factory key must STILL boot (fallback proof)

Phase 3 is not optional. Without it a blinking LED in phase 5 proves nothing —
an unsealed board boots anything.

Run section 0b FIRST: phase 5b signs and flashes the real 2.4MB firmware, and it
is the only proof that acceptance generalises beyond the 33KB blinky. Without a
built seedhammerii-*.uf2 in the fork, phase 5 now refuses rather than skipping.

IF ANY PHASE FAILS, THE REHEARSAL IS NOT GREEN. Do not touch the engraver.

Dry runs: drop --execute to preview a phase. Safe on 0/1/2/4; on 3/5/6 it only
prints. Keep rehearsal-work/ until section 3 is COMPLETE — it holds the keys
that the SH2 tooling checks yours against.


3. REAL SEEDHAMMER II — THE IRREVERSIBLE PART
--------------------------------------------------------------------------------
UNPLUG THE PICO FIRST. A consumed rehearsal board answers with plausible values.
BOOTSEL = hold the white button under the control board while plugging in USB.

STAGE YOUR RECOVERY IMAGE BEFORE YOU START. It is the safety net this whole
procedure is priced on, and you do not want to be downloading firmware at 2am
with a machine that will not boot:

    gh release download v1.4.3 --repo seedhammer/seedhammer --pattern '*.uf2' \
      --dir ~/.sh2
    picotool info -a ~/.sh2/seedhammerii-v1.4.3.uf2 | grep -i signature
    # must say "signature: verified"

STABILITY: an interruption during (d) costs a slot outright — re-running
`otp load` on a half-written slot FAILS (the bootrom refuses to rewrite a
programmed ECC row). Short cable, straight into the machine, no hub, laptop on
AC with sleep disabled, and do not touch the bench during (d) and (f).

    R=../mnemonic-engrave/scripts/pico2-bootkey-rehearsal.sh

  a) MANDATORY GATE — read every line (read-only). You should already have run
     this back in section 0a; run it again now, immediately before the writes,
     so the state you are about to act on is the state you just read:
        $R --sh2-precheck

     It asserts, and STOPs on any failure:
       * slot 0 holds SeedHammer's key -> this really is an SH2, and the
         official-firmware recovery path is intact
       * SECURE_BOOT_ENABLE = 1, KEY_VALID = 0x1, KEY_INVALID = 0
       * spare slots 1-3 empty across ALL 16 rows each
       * all four page-lock rows zero -- the ONLY read-only way to learn
         whether a second key can ever be added. Non-zero = this procedure is
         impossible on this device.
       * CRIT1/BOOT_FLAGS1 redundant copies consistent
     It also PINS this device's CHIPID, which (e) and (g) re-check. Skipping (a)
     silently downgrades that wrong-device check.

     ANY FAIL HERE IS A FACT ABOUT YOUR DEVICE, NOT A TOOL BUG.
     Do not run (b)-(g). Go read the runbook.

  b) Make and back up your key -- OUTSIDE every git repo:

        mkdir -p ~/.sh2 && chmod 700 ~/.sh2
        openssl ecparam -name secp256k1 -genkey -noout -out ~/.sh2/sh2-boot-key.pem
        chmod 600 ~/.sh2/sh2-boot-key.pem

     NOT inside the seedhammer fork. Its .gitignore covers only
     seedhammerii-*.uf2 and _artifacts, its remote is PUBLIC, and one `git add
     -A` would publish a permanently valid boot key for the machine that
     engraves your seed backups. OTP cannot be un-burned.

     Record the fingerprint so you can always tell which key is which:
        openssl ec -in ~/.sh2/sh2-boot-key.pem -pubout -conv_form uncompressed \
          -outform DER | tail -c 64 | sha256sum

     Back it up NOW, off this machine (encrypted: `openssl ec -in
     ~/.sh2/sh2-boot-key.pem -aes256 -out sh2-boot-key.enc.pem`). Lose it and
     you can never sign another update for this machine.

     NEVER re-run this step. If the file is missing later, you have LOST the
     key -- stop and read the runbook's Recovery section. Generating a second
     key silently gives you two files that sign differently.

  c) Build the OTP json (touches no device; asserts the hash two ways):
        $R --make-otp-json --key ~/.sh2/sh2-boot-key.pem --slot 1 --out ~/.sh2/my-otp.json

  d) FIRST IRREVERSIBLE WRITE — burn the hash:
        picotool otp load ~/.sh2/my-otp.json

  e) THE GATE. Read-only, compares all 16 rows:
        $R --sh2-verify-slot 1 --key ~/.sh2/sh2-boot-key.pem

     IF THIS FAILS: the slot is not valid yet, so the machine still boots
     normally. Move to slot 2 by re-running the WHOLE sequence with 2:
        $R --make-otp-json --key ~/.sh2/sh2-boot-key.pem --slot 2 --out ~/.sh2/my-otp-2.json
        picotool otp load ~/.sh2/my-otp-2.json
        $R --sh2-verify-slot 2 --key ~/.sh2/sh2-boot-key.pem
     ...then use 0x4 in (f) and 2 in (g). You get three attempts total
     (slots 1, 2, 3). Do NOT jump straight to (f) with a different value --
     that would validate a slot you never burned.

  f) SECOND IRREVERSIBLE WRITE — only after (e) passes, and only for the slot
     (e) just verified:
        picotool otp set -s BOOT_FLAGS1.KEY_VALID 0x2   # slot 1. slot 2 -> 0x4, slot 3 -> 0x8
     Use `otp set -s` (OR-in), never `otp load`, for this field -- otp load
     attempts to clear bits and will fail.

  g) CLOSE THE LOOP — verify the write actually landed (read-only):
        $R --sh2-verify-valid 1 --key ~/.sh2/sh2-boot-key.pem

     A bare `picotool otp get` is NOT enough here: an interrupted redundant
     write can print the expected value alongside a WARNING and still be
     degraded. This mode fails closed on that, checks KEY_VALID is exactly
     0x1|slot-bit (slot 1 -> 3, slot 2 -> 5, slot 3 -> 9), KEY_INVALID is 0,
     and all three BOOT_FLAGS1 copies agree.

     If KEY_VALID reads LOW, the write was interrupted -- just re-run the
     identical (f) command. It only sets bits, so repeating it is safe. Do NOT
     burn another slot and do NOT start re-signing.


4. SIGN AND UPLOAD (repeatable forever, zero OTP cost)
--------------------------------------------------------------------------------
    env VERSION=$(git rev-parse HEAD) nix run .#build-firmware
    FW=$PWD/seedhammerii-$(git rev-parse HEAD).uf2
    nix develop --command ../mnemonic-engrave/scripts/sign-firmware.sh \
        $FW ~/.sh2/sh2-boot-key.pem
    picotool load --verify ${FW%.uf2}.signed.uf2
    picotool reboot

sign-firmware.sh writes a NEW file (<img>.signed.uf2) and never touches its
input — so the unsigned build keeps matching CI, and a stray tab-complete onto
the official release cannot destroy your recovery image (it refuses that
outright). Flash the .signed.uf2, not the input.

sign-firmware.sh proves the signature offline before you flash: it asserts the
digest is unchanged after embedding the signature, verifies it with openssl,
checks the embedded bytes match, requires exactly 2 metadata blocks, and
requires picotool to report "signature: verified".

Expect "(UNLOCKED)" on the version line afterwards. That is CORRECT — the
firmware only reports "locked" when SeedHammer's key is the sole valid one.
Secure boot is still enforcing; it now trusts two keys.

TWO RULES:
  * NEVER revoke SeedHammer's slot-0 key. It is your only recovery path —
    official releases are signed by it (verified), so you can always flash a
    stock UF2 to get a working machine back.
  * If firmware does not boot but step (e) passed, the hash is PROVEN correct.
    It is a signing problem — re-sign (fresh nonce) and re-flash.
    DO NOT burn another slot.
